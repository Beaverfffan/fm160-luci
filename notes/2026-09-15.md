### apk v3（ADBd）容器格式 —— 踩坑与破解
**结论：apk v3 = `ADBd` 魔数 + offset 4 起的 raw deflate 流**
- 里面**没有** gzip(1f8b)/zstd(28b52ffd)/xz 魔数 → 按魔数探测全部落空
- 是 **raw deflate**（`zlib.decompressobj(-15)`），必须从 offset **4** 开始
- 解出内容以 `ADB.pckg` 开头 = control 段（包名/版本/arch/license/依赖）
- 解出的**不是标准 tar**（NUL 分隔字段、无 512 对齐），`tarfile.open()` 必然失败
  —— 别据此判定"解压坏了"
- 用 docker + Alpine 的 `apk verify`/`apk manifest` 可拿权威结果，
  但 **Docker Hub 拉不动**（`Retrying in N seconds` 死循环），放弃
- 最省事的验证是**构建日志里的 `.pkgdir` 清单**（格式无关）

## BE14000 三项问题排查与修复（下午）

### ① 万兆 WAN 口"协商 100M" —— 实测是**上报错误**，不是限速

真机证据（用接口计数器测，不信 ethtool 自报）：
| 采样窗口 | 实测接收速率 |
|---|---|
| 8 秒 | **412 Mbps** |
| 6 秒 ×5 | 114.8 / **607.8** / 220.0 / **504.2** / 98.0 Mbps |

链路始终自报 `100 Mb/s`，但 100BASE-TX 物理上限就是 100 Mbps。
默认路由 `via 192.168.50.1 dev wan`，同期 `sfp` 口几乎零流量 —— 确认走的就是 WAN 口。

**根因**（上游 `744` 补丁的说明原文）：
> `rtl8261c_cg_probe()` 先调 `rtl826x_probe()`，它会按 vendor version 寄存器
> 请求 `rtl8261n.bin` / `rtl8264b.bin`，之后才请求 `rtl8261c.bin`。
> 只装了 `rtl8261c.bin` 的机器因此**一直 defer，最终绑到通用 Clause 45 驱动**。
> 除了跳过 RTL8261C 初始化，**那个驱动会上报错误的协商速率**。

我们镜像里确实只有 `rtl8261c.bin`。dmesg 里同一 PHY（`mdio-bus:00`）
**探测了两次**，正是 defer→重试的表现。

**修复**：从 `flint4-offload-blogic-review` 分支引入
`744-net-phy-realtek-fix-RTL8261C-firmware-probe.patch`。

4. natflow 的 `mtk_ppe_offload1.c` 里**没有任何 DSA tag 处理**，只有 MxL862xx 那套
   `(outer VID << 4) | port` 编码（见 995 补丁里 `struct flow_offload_hw_path_fake` 的注释）

→ PPE 为交换口编程流时从不生成 YT922x 端口 tag → offload 后报文丢失（断网），
   流反复失效重装（高负载）。

**为什么不能直接复用**：`dsa_port` 是 **u16**，而 `yt922x_4b_port_tag()` 的输出
`YT922X_4B_TX_PORT_M = GENMASK(13,5)`（port 7 → 0x1000，port 8 → 0x2000），
`(tag << 4)` 必然溢出 u16。

**修复**：新增
`996-0001-hwnat-support-yt922x-4b-port-tag-offload.patch`，
在 `mtk_ppe_offload1.c` 里**从目的端口号现算 tag**，作为外层 VLAN TCI 压入
（与上游做法一致），并在一层 VLAN 已被占用时拒绝 offload 交给软件路径。
v4 / v6 两个 prepare 函数都改了。

> 补丁用「先改文件、再 `diff -u` 反向生成」的方式产出，避免手算 hunk 行数出错。
> 这个手法值得复用。

### 995 补丁到底改了什么（决定性事实）


| flint4 补丁 | 改的文件 | 在 x-wrt 下 | 处理 |
|---|---|---|---|
| `967-41` 四字节端口 tag offload | `mtk_ppe_offload.c` | **死代码** | ✅ 已镜像进 `mtk_ppe_offload1.c`（996 补丁） |

| `967-43` 网桥流 key（跳过 YT922x CPU tag） | `mtk_ppe.c` | **死代码** | ⛔ 不适用，见下 |

### 关键判据：`__mtk_ppe_check_skb()` 是整条 RX 网桥链的唯一宿主

`ETH_P_XDSA` / 网桥流 key 的计算就在 `__mtk_ppe_check_skb()`（`mtk_ppe.c:790`）内，
而该函数在 x-wrt 下**不可达**（调用点 `#if 0`，`nm vmlinux` 也确认符号不存在）。
所以 967-43/967-44/967-50 的 `mtk_ppe.c` 部分**不是"忘了迁移"，而是天然不适用**。

natflow 的 `mtk_offload_check_rx_v2()` 里**完全没有 DSA tag 感知**
（`grep -c 'DSA_TAG_PROTO\|dsa_ptr'` = 0，只有 1 处 `dsa_port` 字段）。

### ⚠️ 由此得出的重要架构结论

**`bridger`（跨交换芯片网桥 offload）在 x-wrt/natflow 下无法工作**：
1. **安装侧**：`ndo_setup_tc` 被删除 → tc flower 规则**没有入口**可编程进 PPE
2. **接收侧**：RX 网桥流匹配挂在被禁用的 `__mtk_ppe_check_skb()` 里

这是**加速栈层面的结构性差异**，不是 tag 编码不匹配能修的。
影响：网桥转发的流量**回退到软件转发**（不会断网，但不受硬件加速）。

**但用户实测的"高负载一加硬件加速就断"是另一回事** —— 那是 natflow 自己的
routed/NAT offload 路径缺 YT9224 tag 导致的，已由 996 补丁修复。

## 读 OpenWrt 编译日志的"假错误"（今天踩了两次）

`package/kernel/linux` 的安装规则会把整条 shell 命令回显到日志，

**可靠判据**（看行首，别看关键词）：

```bash
grep -c '^ERROR: module' build.log                      # 真错误 → 0
grep -c 'else echo "ERROR: module' build.log            # 命令回显 → 548
grep -nE '^ERROR:|^make.*\*\*\* \[' build.log | grep -v 'Error 1 (ignored)'
grep -nE 'BUILD rc=' build.log                          # 有这行才是真的结束了
```

另外两点：
- `arm-trusted-firmware` 的 `install-bin-trusted-firmware-a-mt79xx-...` 报

  **不要只看日志尾部**（长编译时尾部可能几分钟不变）

## natflow 断网根因找到并修复（2026-09-15 晚，真机 192.168.15.1）

网络回到 15 网段：本机 192.168.15.129、Ubuntu 192.168.15.157、路由器 192.168.15.1。
设备刷的是本轮 V2 固件（revision `r0+36478-baa3c14d15c`），**能启动，循环重启已解决**。
**内存实测 2,030,200 KB ≈ 1.94 GiB → 证实 GL 规格 DDR4 2GB，DTS 写 2GiB 是对的。**

### 复现（用户给的条件是关键）
Windows = lan2（2.5G），Ubuntu = sfp（10G），**两口都在 YT9224**；Ubuntu:5201 跑 iperf3。
```
Windows→Ubuntu: 首秒 391M~1.2G，之后全程 0.00（偶尔短暂恢复再归零）
```

### 定位（开关对照，双向可复现）
- `echo disabled=1 > /dev/natflow_ctl` → **2.36 Gbit/s 稳定** ✅
- `echo disabled=0 > /dev/natflow_ctl` → 首秒后**全程 0** ❌
→ **natflow 100% 是元凶。**

逐秒采样（`/sys/class/net/*/statistics` + `/sys/kernel/debug/ppe*/entries`）：
natflow 开启时首秒过后**所有接口计数全归零（连 lan2_rx 都是 0）**
→ 不是路由器丢包，是**反向 ACK 路径断 → 发送端 TCP 停发**。
natflow 关闭时 `lan2 rx → sfp tx` 正常，但**全程经 eth1(CPU) 且 br-lan 计数为 0**、CPU ~30%
（即 LAN↔LAN 走 CPU 软件转发，YT9224 硬件桥接没生效 —— 独立问题）。

### 根因
`natflow-boot.init` 的 `ifname_group_type` 出厂值 `0 = fastnat_for_all`，
**LAN↔LAN 二层桥接流也被纳入快转**；而 `natflow-zone.init` 用 `fw3/fw4 -q zone` 解析
zone 成员，DSA 下防火墙 zone **只返回 L3 设备**：
```
fw4 -q zone lan → br-lan      （仅此一个！lan1~8/sfp 只是桥成员，不在列表里）
```
→ natflow zone 表只有 `lan_zone 0=br-lan` → 不认识 lan2/sfp 是 LAN 口 →
无法判断是同区二层流 → 按路由流快转 → 出口算错 → 断。
**非 DSA 机型 LAN 就是一个 br-lan，所以此坑从未暴露。**

### ✅ 修复（已在本机生效并持久化到 uci）
```sh
uci set natflow.main.ifname_group_type='2'      # 2 = fastnat_ifname_group_bypass
uci -q delete natflow.main.ifname_group
for i in lan1 lan2 lan3 lan4 lan5 lan6 lan7 lan8 sfp; do
    uci add_list natflow.main.ifname_group="$i"
done
uci commit natflow && /etc/init.d/natflow-boot start
```
实测：LAN↔LAN **2.31~2.35 Gbit/s 稳定**（反向 1.90G）；LAN↔WAN **BND 20/18、CPU 2.7~6.2%
（硬件卸载保住）**；natflow 仍 enabled=1。

### ⚠️ 走过的弯路（别重犯）
| 配置 | LAN↔LAN | LAN↔WAN 卸载 |
|---|---|---|
| `type=0`（出厂） | ❌ 掉 0 | ✅ |
| `type=0` + 把 lan1~8/sfp 加进 `lan_zone` | ❌ 仍掉 0（**zone 不是充分条件**） | 未测 |
| `type=1` + group=`wan` | ✅ 2.36G | ❌ **无卸载、CPU 14~23%（退化）** |
| **`type=2` + group=LAN口** | ✅ 2.31G | ✅ **BND 20/18 / CPU ~5%** |
`type=1` 语义是「流的**所有**接口都要在组内」→ LAN→WAN 因 lan2 不在组内被排除 → 全退化成软件快路。

### 结案：996 tag 补丁不需要
实测证明 natflow 的 995 补丁**本身含 DSA 出口处理**（`mtk_ppe_offload1.c` 有
`#include <net/dsa.h>` + `mtk_foe_entry_set_dsa()`），硬件卸载在 LAN↔WAN 上工作正常。
**之前"必须写 996"的推断是错的，以实测为准。**
PPE 表解码：`mtk_foe_entry_set_dsa()` 写 `l2->etype = BIT(port)`；debugfs 的 `etype` 经
`ntohs()` 反解 —— `etype=2000` → `BIT(5)` = DSA 端口 5。
debugfs 打印语义：`eth=A->B` 是**源→目的**（`h_source` 在前）。

## 【更正 + 定案】LAN↔LAN 不能硬转的真根因（推翻上午的 999-Z-0300 结论）

用户带回作者原话：**x-wrt 关掉交换机 offload 是故意的**，就是为了让 LAN↔LAN 走 PPE 硬转；
真正的 bug 是**硬转失败**。上午判定的 `999-Z-0300-dsa-disable-offload.patch` 是"设计选择"，

## 23:55 WED 与风扇排查（真机实测，192.168.15.1 = GL-BE14000）

### 结论先行
**WED 在驱动层是生效的，natflow 的 WED 分支也开着**；但 natflow 在 MT7988 上
**只把 `端口 → PPE → WiFi` 这一段交给 WED**，`WiFi → 端口`（终端上传）仍走
`WiFi → CPU → PPE → Port`（作者 README 的路径表原文），且其 WED 支持列表里
**只有 MT7622 / MT7981 / MT7986，没有 MT7988**。所以"WED 没生效"的观感是对的，
只是范围问题，不是配置错。

### 证据链（都实测）
1. 驱动：`mt7996e` 参数 `wed_enable=Y`（来自 JiaY-shi 提交 `7dc923b7d83` 的
   `MODPARAMS.mt7996e:=wed_enable=1`）；dmesg 有
   `mt7996e 0000:01:00.0: attaching wed device 0 version 3` +
   `mt7996e_hif 0001:01:00.0: attaching wed device 1 version 3`。
2. WED 平台设备：`15010000.wed` / `15012000.wed` / `15014000.wed`，调试接口在

   计数器随无线流量增长。WO 固件只给 wed0 加载（`platform 15010000.wed: MTK WED WO

## 00:00（9-16）事故：LuCI 报 "left-hand side expression is null" —— 我的一条引号坏掉的内联 SSH 命令造成

### 症状
用户在 LuCI 看到 `Unhandled exception during request dispatching / left-hand side
expression is null`（runtime.uc:133，来自 dispatcher.uc:991 → runtime.render）。
同时：`logread` 报 `Failed to find log object: Not found`；`ubus call session create`
报 `Command failed: Not found`；`ubus list` = **0 个对象**；
`/etc/init.d/rpcd status` 报 `Command failed: Not found` + `inactive`。

### 根因（确证）
**有两个 `ubusd`，而 `/var/run/ubus/ubus.sock` 这个路径被野的那个抢占了：**

```
pid 1240   /sbin/ubusd      uid=ubus(81)   ppid=1(procd)  ← 真正的总线，20 个 socket
pid 13134  ubusd            uid=root       ← 野的
   ppid=13129 → cmdline 是我那条引号被吃坏的内联命令残余：
   'ash -c  echo \"--- 进程 ---\" ps w | grep -E \"wifi|rmmod|ubusd|netifd\" ...'
```

**机制**：那条命令的引号在 `本地 bash → ssh Ubuntu → sshpass → ssh router` 四层里被逐层剥掉，
grep 的**模式串 `"wifi|rmmod|ubusd|netifd"` 被当成管道命令执行**了，于是
`ubusd` **以 root 身份被启动**，并 unlink + 重新 bind 了 `/var/run/ubus/ubus.sock`
（`/proc/net/unix` 里能同时看到两个 listening inode：真总线 3376、野的 21784）。
新连接（CLI / uhttpd）全落到空总线上 → LuCI 拿不到 `session`、`logread` 拿不到 `log`、
init 脚本连不上 procd → 全崩。

**处理**：kill 掉野 ubusd(13134) 与泄漏的 `rt.sh`/`sshpass`。
但 socket 路径已被换成死 inode，**必须重启**才能让 ubusd 重新 bind、各守护进程重连。
（真 ubusd 的 20 个 socket 仍在，但按路径已不可达。）

### 教训（写进纪律）
**绝不要把多行 shell 直接内联**穿过这条嵌套 ssh 链 —— 一行里只要有一个引号被吞，
grep/sed 的模式串就会变成命令被执行（这次执行了 `ubusd`、`netifd`、`rmmod`）。
一律：本地 Write 落盘 → `scp` 到 Ubuntu → `sh /tmp/x.sh`（或 `rt.sh "sh -s" < x.sh`）。
另外 `pkill -f <模式>` 会把**自己这条命令**也匹配掉（本次被 killed 两次，exit 127）→
清理要按 **明确的 PID** kill，或用 `pgrep -x`。
