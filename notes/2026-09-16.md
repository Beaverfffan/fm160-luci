## 07:50~08:40 —— MXL862_8021Q 与 YT922X_4B 的 tag 编码差异（为作者重写做准备）

报告：`BE14000-fixes/DSA-TAG-ENCODING-MXL862-vs-YT922X.md`

**共同点**：两者都是 **4 字节、TPID 0x8100、`[81 00][16 位 ctrl]`** 的「802.1Q 形状」CPU tag
（MXL 官方注释明说 "encode port information in 802.1Q VLAN tags instead of the native
8-byte special tag"）。**这正是 PPE 能用 `mtk_foe_entry_set_vlan()` 发它们的原因。**

**不同点（ctrl 里装什么）**：
- **MXL862_8021Q**：ctrl = `dsa_tag_8021q_standalone_vid(dp)` = `DSA_8021Q_RSV | SWITCH_ID | PORT`
  —— 一个**保留 VID**。信息量 > 端口号（还有 switch_id）→ **必须额外携带**
  → 才有 `path->dsa_port |= vid << 4` 的打包 + PPE 侧 `(dsa_port & 0xff00)` 的解包。
  低半字节留端口号是因为还要算 QDMA 队列（`dsa_port_rank[port]`）和
  MXL tagger 的 `skb_set_queue_mapping(skb, dp->index)` per-port TX 队列约定。
- **YT922X_4B**：ctrl = `yt922x_4b_port_tag(port)` = `BIT(port) << 5`，
  **纯端口位图，没有 switch_id/VID → 不需要额外携带**，所以 `999` 补丁只需 `dsa_port`。

**YT922X_4B 自己的坑**（重写时最容易漏）：
1. **TX/RX 布局不同**：TX 端口**位图**在 `13:5`（9 位，端口 0..8，`port>8` 返回 0）；
   RX 源端口是 **4 位端口号在 `7:4`**。
2. RX 的 `15:8` 是 **trap reason**（0=正常转发，4=未知组播），tagger 靠它决定
   `dsa_default_offload_fwd_mark()`。
3. **别复用 8 字节格式的位**：8B 的 `BIT(9)`=FORCE_DST、`GENMASK(12,10)`=PRIO
   在 4B 里正好压在端口位图上（bit9=端口4，bit10~12=端口5~7）。头文件专门警告过。
4. YT tag 在**客户 VLAN 之外层**（`yt922x_4b_tag_xmit()` 先插客户 tag 再 push YT tag），
   线上一层接入 VLAN 口是 `[81 00|yt-ctrl][81 00|vid][payload]` 两层。

**给重写的建议**（已写进报告 §5）：
- 把编码归还 tagger：加回调 `u16 (*flow_offload_port_tag)(const struct dsa_port *dp)`，
  MXL 返回 standalone_vid、YT 返回 `yt922x_4b_port_tag()`、其它返回 0 → 回落 `set_dsa()`。
  这样 `net/dsa/user.c` 里那三行 MXL 特判可以删掉，也不用再 `#include <linux/dsa/8021q.h>`。
- `flow_offload_hw_path` **新增 `u16 dsa_port_tag`**（最终要写进 802.1Q TCI 的 ctrl），
  `dsa_port` 保持"纯端口号"。下游从三路 `if/else if/else` 简化成
  `if (dsa_port_tag) set_vlan else set_dsa`，**`999` 补丁即可退役**，端口号也不再被 4 位限制。
- **层序别改坏**：`mtk_foe_entry_set_vlan()` 按调用顺序决定内外（layer0→`vlan1` 外层，
  第二次→`vlan2` 内层）。当前 DSA 块在前、`FLOW_OFFLOAD_PATH_VLAN` 在后 → 顺序正确。
- **已知缺口**：`999` 只写了 YT tag **一层**，没写客户 VLAN。真机 `br-lan` 的
  `vlan_filtering=0`（实测），所以现在完整正确；**一旦开 `bridge-vlan-filtering`，
  硬转出口会少一个客户 tag → 又是静默丢帧**。建议写进重写需求。
- PPE 里 `dest->dev->dsa_ptr->tag_ops->proto == YT922X_4B` 这条判定能成立，
  是因为 `dest->dev` 已被 hook 换成 conduit（`eth1`）—— 与上一节结论互相印证。

## 08:25~08:50 —— 追问：能否在 x-wrt 复用 MXL 的「直接带 VLAN id」打包

**问题**（用户）：原厂只有 8b，4b 是 JiaY-shi 为主线加速自己做的。能不能在 x-wrt 复用
MXL862 那套打包方式（直接带 VLAN id），性能理论上会更高？

**答案：不需要，也不能直接搬；性能不会更高。**（报告 §八）

1. **MXL862 的打包不是性能设计，是接口缺陷的补丁**：MxL862xx **芯片本身就是用 VLAN 标识端口**
   （tagger 名 `tag_mxl862xx_8021q.c`，注释 "instead of the **native 8-byte** MxL862xx special tag"）。
   x-wrt 的 `dsa_port |= vid<<4` 唯一原因是 `flow_offload_hw_path.dsa_port` 只有**一个 u16**，
   装不下「端口号 + standalone VID」；而 DSA hook 是唯一能拿到 `dp` 的地方。副作用：端口号被限 4 位。
2. **机制层面已经在复用**：`999` 就是让 YT9224 走同一条 `mtk_foe_entry_set_vlan()` → 硬件插 `81 00|ctrl`。
3. **编码不能搬**：YT9224 4b 模式下芯片把这 16 位当**端口位图**（13:5）解析，塞 VID 就解不出目的口。
   想「端口由 VLAN 决定」需要芯片支持该模式 —— 驱动里**完全没有**实现；
   CPU tag 寄存器只有两个模式位（`TX_MODE`/`TX_TYPE`），另有 **`TX_CTAG_OP`=BIT(2)、
   `TX_STAG_OP`=BIT(3)`** 说明**客户 VLAN 是芯片独立处理的，不需要靠 ctrl 里的 VID**。
   `YT921X_CPU_TAG_TPID`(0x80010) 硬件默认 **0x9988**（= `ETH_P_YT921X`，非官方注册 ID）。
4. **「带 VLAN」4b 模式天然支持 —— 靠第二层 tag**：`yt922x_4b_tag_xmit()` 先调
   `yt922x_vlan_xmit()`（插客户 PVID）再 push YT tag → 线上 `[81 00|yt-ctrl][81 00|客户 vid][payload]`。
   而且驱动把 4b 与 802.1Q **硬绑定**：
   `"YT9224 VLAN filtering requires 802.1Q and four-byte CPU tags"`（`yt922x_dsa_port_bridge_join`）
   —— **VLAN filtering 只在「4b + 802.1Q」下被允许**，JiaY-shi 做 4b 的动机之一就是它。
   `mtk_foe_entry_set_vlan()` 本来就支持两层（vlan1/vlan2）→ **"带 VLAN"不用改编码，
   只需 PPE 写第二层 tag**（`999` 目前只写了一层，这才是开 VLAN filtering 前要补的）。
5. **性能不会更高、也没余量**：数据面动作完全相同（一次 vlan_layer 设置 + 写 vlan1/vlan2），
   实测已 TCP 9.38~9.39 Gbit/s / UDP 9.55 / CPU 6~8% / 重传 0.003%。
6. **值得复用的是「两层 tag 的调用顺序」这个做法**（端口 tag 先写=外层，客户 tag 后写=内层），
   而不是复用一个塞了 VID 的 u16 字段。接口抽象（`dsa_port_tag` + tagger 回调）才是正解。
7. **待向原厂确认**：「YT9224 是否支持用 VLAN 表决定 CPU 出口端口」本树查不到结论
   （无实现、无文档引用）→ 问 `Kyle switch <kyle.switch@motor-comm.com>` 或 JiaY-shi。
   在拿到肯定答复前，4b 位图模式是唯一可验证的路线。

## 10:20~10:25 —— 两个边界问题（加速范围 / 端口号位宽）

报告：`BE14000-fixes/DSA-PORT-RANGE-ANALYSIS.md`

### Q1 加速范围是否比上游小 → **不小**（YT 路径完全一致，其他路径反而更宽）
- YT922X_4B 三种情形（正常/开 vlan_filtering/端口>8）与上游**逐条相同**
- 我们**更宽**的三处（都是**缺白名单兜底**，不是优点）：
  ① 未知 tagger：上游 `default: return -EOPNOTSUPP` 拒绝；我们 → tag=0 → **用 `set_dsa()` 卸载**
  ② MXL 端口 0：上游 `!dp->index` 拒绝；我们返回非零 vid → 卸载
  ③ MTK 索引 ≥32：上游拒绝；我们仍 `set_dsa`（rank 被守卫跳过）
- 本机只有 `mtk`(MT7530) / `yt922x_4b`(YT9224) 两个 tagger → 不触发
- **若要补齐**：给 `net/dsa/tag_mtk.c` 也加回调（返回 0 = 我要原生 MTK tag），
  并把 `user.c` 的契约改成"**没有回调 = 不许卸载**" → 消除 `0` 的歧义
  （"没回调" vs "回调返回 0"）。代价：补丁 A 从 5 文件变 6 文件。

### Q2 掩码超 4 位是否会让 MTK 加速失效 → **不会**（且我们修掉了旧代码一个真 bug）
1. **`& 0xf` 从来没作用在 tag 入参上**：旧代码 `u16 dsa_port = dest->dsa_port; if (dsa_port & 0xff00) dsa_port &= 0xf;`
   这个局部副本**只服务队列查找** `dsa_port_rank[dsa_port]`；
   `set_dsa()` 收 `dest->dsa_port` 原值、`set_vlan()` 收 `dest->dsa_port >> 4`。
2. **`MTK_DSA_USER_PORT_MAX = 32`**（`mtk_eth_soc.h:34`），`u8 dsa_port_rank[32]`（:1485），
   所有访问点都有 `<32` 守卫（`mtk_ppe_offload1.c:334/468`、`mtk_eth_soc.c:3880/3919/5211`）
3. **真机端口号**（DTS `reg` = `dp->index`，`mt7988a-glinet-gl-be14000.dts`）：
   - MT7530(eth0,mtk)：lan5=0 lan6=1 lan7=2 lan8=3 **cpu=6**（`MT7530_NUM_PORTS=7`）
   - YT9224(eth1,yt922x_4b)：sfp=0 lan1=4 lan2=5 lan3=6 lan4=7 **cpu=8**（`YT922X_PORT_NUM=9`）
   - **全机最大 8** → 4 位（0..15）装得下 ✅
4. **`set_vlan()` 无 12 位 VID 掩码**：`l2->vlan1 = vid;` 直接赋值，`vlan1` 是 **u16**
   （`mtk_ppe.h:113` `struct mtk_foe_mac_info { u16 vlan1; u16 etype; }`）
   → **lan4 的 ctrl = `0x1000`（bit 12）完整保留**，若掩码成 `VLAN_VID_MASK` 就会变 0 → 静默丢帧
   （上游 commit message 专门警告过这条）
5. **旧代码的真 bug（MXL）**：`DSA_8021Q_RSV = 3<<10 = 0x0c00`，`DSA_8021Q_PORT` = VID[3:0]，
   头文件明写 "Must be between 0 and 15"。旧 `(vid << 4)` 在 u16 里截断 →
   **MXL 端口 ≥16：rank 和 tag 双双算错**（index 16 → rank 0、tag `0xc11` 而非 `0x0c10`）。
   我们的双字段结构从根上消掉。
6. **一致性论证**：软件 TX 路径 `mtk_select_queue()` 用 `skb_get_queue_mapping(skb)`
   = tagger 写的**完整 `dp->index`** 查同一个 `dsa_port_rank[]`。
   旧代码让硬转路径对同一端口用低 4 位 → **两条路径不一致**，这才是异常。
7. **唯一硬件边界**（新旧与上游同）：`set_dsa()` 是 `l2->etype = BIT(port)`，`etype` 是 **u16**
   → **MTK 形状端口索引必须 < 16**。本机 MTK 路径最大 6，安全。
   ⚠️ 上游的 `< 32` 判断比硬件能力更松（16..31 会静默产生 etype=0），我们与上游相同，非回归。

## 10:51~11:30 —— v6-test 真机测试：**发现严重回归**（LAN↔LAN 硬转黑洞）

**报告：`BE14000-fixes/V6-REGRESSION-ROOTCAUSE.md`**

### 症状（netns 隔离，sfp↔wan 转一圈，v6 固件）
| 配置 | TCP | 路由器 CPU |
|---|---|---|
| `hwnat=1` | **0.00**（首秒 2.07G 后归零，Cwnd 塌到 1.41KB 不动） | 1.7% |
| `hwnat=0` | **2.75 Gbit/s** ✅ | 34.5% |
- UDP 正向能跑（5.59G，0% 丢包）；**UDP 反向 `-R` 发送端 8.55G / 接收端 0**
- → **软件路径正常，是硬件卸载把流量打成黑洞**

### PPE 证据（`etype` 需字节反转才是真值）
| | v4（工作） | v6（坏） |
|---|---|---|
| 正向（出口 wan/gmac2 非 DSA） | `etype=0008 vlan=0,0` | 同 ✓ |
| **反向（出口 sfp/YT9224 p0）** | **`etype=0008 vlan=32,0`** | **`etype=0100 vlan=0,0`** ✗ |
- `etype=0100`→`0x0001`=`BIT(0)` = **`set_dsa()` 的痕迹**（MTK 私有 tag，YT924 解不出）
- → 反向走了 `else { set_dsa }` ⇒ **`dest->dsa_port_tag == 0`**，而 `dest->dsa_port` 是对的

### 🎯 根因：**natflow 只逐字段传播它认识的字段**
`natflow_path.c`（`build_dir/.../natflow-20260912/`）用**两个不同的 `flow_offload_hw_path_t` 实例**：
```c
u16 orig_dsa_port = 0xffff;
flow_offload_hw_path_t orig = { .dev=..., .flags=... };   /* 临时结构体 A */
orig_dev->netdev_ops->ndo_flow_offload_check(&orig);      /* ← 我们的 hook 写进 A */
if (orig.dev != orig_dev) { orig_dev = orig.dev;
                            orig_dsa_port = orig.dsa_port; }  /* 只回捞 dsa_port */
...
flow_offload_hw_path_t orig = { .dev=orig_dev, .flags=...,
                                .dsa_port = orig_dsa_port };  /* 从零构造 B 交给 PPE */
```
**它根本不知道 `dsa_port_tag` 存在** → B 里该字段零初始化 = 0 → PPE 走 `set_dsa()` → 黑洞。

- `dsa_port` 在 natflow_path.c 里出现 **24 次**（4 处声明/回捞 + **20 处 initializer**，两大代码块 2792~3181 / 4686~5075）
- **要给新字段打通就得改这 24 处第三方 feed 代码**

### 为什么 v4 能工作
旧 `999` **只用 `dsa_port`**（natflow 会传播）+ `dest->dev->dsa_ptr->proto` 判定 →
**没新增字段 → 不触碰 natflow 契约** ✓
→ **`dsa_port` 里 `<<4`/`<<5` 打包不是权宜之计，而是唯一能穿过 natflow 边界的办法。**
上游 `dae51fb51cd9` 把整个 ctrl 塞进 `dsa_port` 也是同一道理（他是 natflow 作者，这约束是硬性的）。

### 结论与选项
| 方案 | 语义分离 | 改 natflow | 能否工作 |
|---|---|---|---|
| v4 旧 `999` | 否 | **否** | ✅ 9.38 Gbit/s |
| 上游 `dae51fb51cd9` | 否 | **否** | ✅ |
| 本方案 `dsa-port-tag` | 是 | **是(24处)** | ❌ 黑洞 |
- **A**：给 natflow 打补丁（保留干净架构，但依赖第三方包内部实现）
- **B（推荐）**：回到 `dsa_port` 载值，与上游对齐，零风险
- **C**：折中（回调返回"要塞进 dsa_port 的值"）—— 16 位装不下「端口号+完整 TCI」
  （YT ctrl 14 位 + 端口号 5 位 = 19），**PPE 侧无法完全消除 tagger 专属解码**，抽象收益有限
- ⚠️ 若要推方案 A，**应先与 natflow 作者确认**

### 附带结论
- **VLAN-filtering 闸门本身是对的**（`yt922x_vlan_xmit()` 确实用 `br_vlan_get_pvid_rcu()` 现读
  PVID 插一层，PPE 复现不了），只是「救不了一个被 natflow 丢掉的字段」
- `tag_mtk.c` 加回调与本次故障无关，可独立保留或随方案一起回退

### ⚠️ 教训（重要，已回灌 skill）
**给 `flow_offload_hw_path` 这类"由外部模块构造并逐字段转拷"的结构体加字段，
不是纯内核改动** —— 必须先查**所有构造者的字段白名单**。
否则字段在内核侧写对了、在到达消费者前被悄悄丢掉，且**症状是静默黑洞**。
本次排查花了很多轮才定位，正是因为一直在内核侧找原因，而问题在用户态之外的模块契约里。

DISTRIB_RELEASE='26.04_b202609121905'      ← 就是上面那个 config 值，**不反映代码**
DISTRIB_REVISION='r0+36564-33b23ac8b42'    ← ✅ 真实：r0+<提交数>-<HEAD SHA>

### 关于"老方案 4 字节 tag"（用户提问）

flint4 的 YT9224 **4 字节 tag 也是 `[81 00][ctrl]` 的 802.1Q 形状**，PPE 也走 `mtk_foe_entry_set_vlan()`。
两者差别**只在 ctrl 的语义**：老方案是**私有端口位图**（`BIT(port)<<5`），8021Q 方案是**标准 VID**。
RTL8366UB 不认识 YT9224 的私有编码 ⇒ 用老方案仍要为 Realtek 另写一套私有协议，
**工作量不省、还多一份私有协议要维护，且社区接受度低**。
而"对齐 bpi r4 pro"恰恰就是**选 8021Q**（mxl862 在 mainline、bpi r4 pro 在用、GL.iNet 自己 PR 也选了它）。
