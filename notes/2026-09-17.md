## 二、硬件事实（从 PR head 的 DTS 与 commit message）

- **SoC MT7987A**（4×Cortex-A53 @2.0 GHz），**1 GiB DDR4**，**8 GiB eMMC**
- **2×2.5G LAN** 走 **Realtek RTL8366UB** 交换机；**1×2.5G WAN** 走 SoC 内置 PHY（`phy15`）
- 按键 reset；LED run(蓝)/system(白)/vpn(白)；UART 115200 8n1
- 分区：GPT / u-boot-env / Factory / FIP / cfg / log / kernel / rootfs（**base MAC 在 Factory 0x4000**）
- **gmac0 = conduit**（`mac-type="gdm"`, `phy-mode="2500base-x"`, fixed-link 2500）→ RTL8366UB **cpu port = port@17**
- **gmac1 = WAN**（`mac-type="xgdm"`, `phy-mode="internal"`, `phy-handle=<&phy15>`）
- 交换机节点在 `&mdio` 下：`compatible="realtek,rtl8366ub"`、**`reset-gpios=<&pio 48>`**
  （⚠️ 最新修订才改成 pio 48，早期是 pio 0；mdio 自己的 reset 才是 `pio 0`）
- 用户口：`port@0`→lan1、`port@1`→lan2，`phy-mode="internal"`

## 三、★ 关键判据（本节全是硬结论）

### 1. 协议号 32 —— 确认空闲
x-wrt 树（`build_dir/.../linux-6.18.44/include/net/dsa.h`）实测：
```
DSA_TAG_PROTO_MXL862_8021Q_VALUE  31
                                 ← 32 空（x-wrt 作者刻意留的）
DSA_TAG_PROTO_YT921X_VALUE        33
DSA_TAG_PROTO_YT922X_VALUE        34
DSA_TAG_PROTO_YT922X_4B_VALUE     35
```
⇒ `RTL8366UB_8021Q = 32` 零冲突。（`xwrt-799-40` 补丁也印证 `YT922X_4B_VALUE 35`）

### 2. tagger 自动带出，不用单独配
`795-10` 的 `drivers/net/dsa/realtek/Kconfig`：
```
config NET_DSA_REALTEK_RTL8366UB
	tristate "Realtek RTL8366UB switch driver"
	depends on NET_DSA_REALTEK_MDIO
	select NET_DSA_TAG_RTL8366UB_8021Q      ← tagger 由 select 带出
```
⇒ `filogic/config-6.18` 只加三项（`NET_DSA_REALTEK`、`_MDIO`、`_RTL8366UB`）即可。

### 3. `generic/config-6.18` 必须加两条 not-set
PR head 的 8 文件里**没有** generic/config-6.18。但新符号若不回答，
**其它 target 的 syncconfig 会遇到未回答 prompt 直接挂**（PR 的 CI 全红就是这个）。
已加：
```

# CONFIG_NET_DSA_TAG_RTL8366UB_8021Q is not set
```

### 4. ★★ x-wrt 的 PPE 加速必须**重放进 995 的活代码**
- `795-01..09`（x-wrt 既有的 MXL862 那组）改的是 **主文件** `mtk_ppe_offload.c` /
  `mtk_ppe.c` / `mtk_eth_soc.c`
- 而 natflow 的 `995-0001` 让 `mtk_ppe.c`/`mtk_ppe_offload.c` **完全不参与编译**（换成 `*1.c`）
  ⇒ **795-01~09 与 795-11 的该文件改动在 x-wrt 上全是死代码**
- 活代码是 `mtk_ppe_offload1.c`，其扩展点**只有 4 处**（实测行号）：
  | 位置 | 作用 |
  |---|---|
  | `net/dsa/user.c:2607` `dsa_flow_offload_check()` | **打包** VID 进 `path->dsa_port` |
  | `mtk_ppe_offload1.c:249` `mtk_offload_get_dsa_info()` | **解包** |
  | `mtk_ppe_offload1.c:398` `mtk_offload_prepare_v4()` | `set_vlan` 分支 |
  | `mtk_ppe_offload1.c:530` `mtk_offload_prepare_v6()` | `set_vlan` 分支 |

### 5. ★ 打包/解包格式（照抄 MXL862，逐字同构）
```c
/* 打包（net/dsa/user.c）*/
path->dsa_port = ((vid & 0x3ff) << 5) | dp->index;
/* 解包（mtk_ppe_offload1.c）*/
*vid = 0xc00 | ((*port >> 5) & 0x3ff);
*port &= 0x1f;
```
- `dsa_tag_8021q_standalone_vid(dp)` = `DSA_8021Q_RSV | SWITCH_ID | PORT`，**RSV 恒占高 6 位（=0xc00）**
  ⇒ 解包用 `0xc00` 硬编码补回，与 MXL 一致
- `mtk_foe_entry_set_vlan(eth, entry, vid)` 返回 int，把 vid 写进 `l2->vlan1`/`vlan2`（PPE 4 字节头）
- ⚠️ **`dsa_port` 是唯一能穿越 natflow 边界的字段**：natflow 逐字段转拷
  (`flow_offload_hw_path`)，不认识的字段一律丢弃 ⇒ **VID 必须打包进去，不能加新字段**

### 6. ⚠️ port 索引 0 合法（与 MXL 不同）
MXL 的 case 是 `if (!dp->index || dp->index > 16) return -EOPNOTSUPP;`（**拒绝 0**）；
MT5000 的 **lan1 就是 port@0** ⇒ 我们的 case **不能拒绝 0**，改用 `dp->index > 4`
（RTL8366UB 最多 5 个用户口）。

### 7. ★★ `include/net/dsa.h` 的协议号分配**必须排在最后**
**踩坑实录**：`795-11` 原样带 dsa.h 的两个 hunk（插 32）。第一次 prepare：
- ✅ `795-10/11/12` 全打上
- ❌ 随后 **`799-02`（YT921x）FAILED at 57/91** —— 因为 795-11 抢先占了"31 后面"的位置，
  而 799-02/27/40 都假设"31 后面紧跟 enum"

**机理**：`795-11` 排在 `799-02` 之前（字典序 795 < 799），但它插进去的 32 破坏了后者上下文。
**修法**：把 dsa.h 段落从 795-11 里**摘出**，单独做成编号最大的
`799-91-net-dsa-add-rtl8366ub-8021q-tag-protocol.patch`（在所有 799-xx 之后应用）
⇒ 值顺序反而更完美：31 → **32** → 33 → 34 → 35。
⚠️ **通用教训**：共享文件（协议号枚举）的插入点必须排在所有既有插入之后。

### 8. ⚠️⚠️ `tmp/.packageinfo` 陈旧 → DEVICE_PACKAGES 不注入
`make defconfig` 后实测 8 个设备包**全是 `=m`**（对照 `~/mt5000` 是 `=y`）。
- `=m` = 只编译**不进镜像** ⇒ 对 eMMC 设备是**致命**的（`mkf2fs`/`blkid`/`blockdev`/
  `kmod-mmc`/`kmod-fs-f2fs` 不在 rootfs 里 → 根文件系统挂不上）
- **修法**：手工 `sed` 删旧行 + 追加 `CONFIG_PACKAGE_<pkg>=y`，再 `make defconfig`（这次会保留）
- 涉及的 8 个包（都在 x-wrt 里存在，实测）：
  `mkf2fs`(utils/f2fs-tools)、`blkid`/`blockdev`(utils/util-linux)、
  `kmod-fs-ext4`/`kmod-fs-f2fs`/`kmod-fs-vfat`(kernel/linux/modules/fs.mk)、
  `kmod-mmc`(modules/other.mk)、`mt7987-2p5g-phy-firmware`(firmware/linux-firmware/mediatek.mk)

### 9. 编号正好接上
x-wrt 的 `generic/pending-6.18/` 已有 `795-01..09`（MXL862 那组）⇒
`795-10/11/12` 直接接上，**零占位冲突**。
`mediatek/patches-6.18/` 的 996/997/998 实测**都不碰** `net/dsa/user.c` /
`mtk_ppe_offload1.c` ⇒ 999 补丁在它们之后应用也精确可打。

## 10:00~10:05 ★ 在 320×240 SPI 屏上播 Bad Apple（成功，30 fps 零丢帧）

**panel-mipi-dbi (ST7789 系) 320×240 TFT，SPI0 @ 52 MHz**（DTS `spi-max-frequency=<52000000>`）。

### ⚠️ 关键结论 1：**不要用 `/dev/fb0` 放视频**
`/dev/fb0` 确实存在（`panel-mipi-dbid` / 320×240 / stride 640 / bpp16），**写它也确实能推帧**
（实测写一次 → `+460,833 B / +18 transfers` = **正好 3 整帧**；再写 → `+307,222 B` = **2 帧**）。
**但**：连写 20 帧后立刻看 SPI = **0 帧**；换条件下 = **1 帧**；单写 + sync + sleep2 = **2~3 帧**。
⇒ DRM 的 fbdev 模拟是**影子缓冲 + 异步脏页刷新**，多次写入被**合并**、吞吐不受控 ⇒ **无法定帧率**。

### ★ 关键结论 2：正解 = 直接走 DRM，双缓冲 + `drmModeSetPlane`
自写 `baplay`（C，74,960 B，aarch64/musl）：
```
open /dev/dri/card0
★ drmSetClientCap(fd, DRM_CLIENT_CAP_UNIVERSAL_PLANES, 1)   ← 少了这句 drmModeGetPlaneResources 返回空！
drmModeGetResources → crtc[0] / connector[0].modes[0] = 320x240@60
planes=1 → plane 34, formats: RG16 XR24   ← RG16 = DRM_FORMAT_RGB565（小端直写，无需 swap）
2 个 dumb buffer(16bpp) + drmModeAddFB2(RGB565) + mmap
每帧：展开 2bpp→RGB565 → drmModeSetPlane(..., buf[i&1].fb, ...)   ← 交替 fb 保证"有变化"
```

### ★ 判据：SPI 计数器反算"真的上屏几帧"
一次 commit = **+153,611 B**（153,600 = 320×240×2 + 11 B 命令）。

## 10:45~11:05 bad apple 独立播放应用（分支 `bad-apple`）+ 修掉真机画面错位

用户报：屏上「同一内容重复的条带、只占上半屏」。照片确认 = 上半屏被压扁的整帧 + 下半屏条带。

### 根因一：拷行寻址（真 bug，编译不报）
```c
memcpy(dst + y * frame_w, frame + (size_t)y * h.width * 2, (size_t)w * 2);   /* frame 是 uint16_t* */
```
`y * h.width * 2` 让目标第 y 行去取源第 **2y** 行（多跳一倍）⇒ 整帧压进上半屏；
且 y ≥ 120 后源行号已越出 `malloc(320*240*2)` ⇒ 读到堆残留 = 下半屏重复条带。
- **修法**：抽出 `blit(dst, dst_pitch, frame, src_w, w, rows)` —— 源按**元素**偏移、目标按 **pitch** 走
  （顺带把「帧缓冲 pitch 可能 > w*2」的隐患一起兜住）
- 教训：**指针类型换了，乘法要跟着改**；`uint8_t*→uint16_t*` 时最容易漏 `*2` 残留。
  这类 bug 语法检查/日志/`--info` 全拦不住 —— 只能靠**导出单帧**核对

### 根因二：DRM master 竞态（安静地 0 帧）
`drmModeSetPlane: Permission denied`（EACCES）—— 面板（LVGL）还占着 DRM master，
有几次播放"起来了但 0 帧"，屏上纹丝不动（差点误判成"没装上"）。
- **修法**：① 打开卡后 `drmSetMaster()` 失败则每 100ms 重试（≤4s）；② 提交遇 EACCES/EPERM
  抢回 master 再重试；③ init 里 stop 面板后再 start 播放器
- 真机日志印证：`等了 0.1s 才拿到 DRM master（面板刚退出）`

### 新增能力：`--dump N out.ppm`（不碰 DRM 的离线自检）

  ⚠️ 触摸设备**按 `ABS_X|ABS_Y` 能力位**选（`abs=0x3`）；**别用 BTN_TOUCH 当判据** ——
  `1UL << 0x14a` 溢出 64 位 ⇒ 用 `unsigned char keybits[(KEY_MAX/8)+1]`。
- 开火判定读 `gamekeydown[]` ⇒ **按下与释放落在同一 35 Hz tick 内 = 没按过** ⇒ 动作**最小按住
  `pulse_ms`（默认 120 ms ≈ 4 tic）**；动作三来源取或 `src_latch | src_pulse | src_stick`。
  头文件宏冲突：`<linux/input-event-codes.h>` 与 `doomkeys.h` 的 `KEY_*` 大面积重名 ⇒ 引中立 `ACT_*` 层。
- 单点屏约束：手指按着 FIRE 就没法滑动转向 ⇒ **锁定式按钮**（点一下锁住/再点解开）+
  **轻点画面 = 单发** + **摇杆原点跟随**（超半径时把原点拖回半径内）。
- 交叉编译 `aarch64-openwrt-linux-musl-gcc`（OpenWrt GCC 14.4.0）；libdrm 头**两处 `-I` 都要**；
  `Makefile.be14000` 的 `SRC_DOOM` **必须含 `dummy.o`**（提供 `net_client_connected` / `drone`）；
  ⚠️ `make CFLAGS=` 会覆盖 Makefile 内 `CFLAGS +=` ⇒ 必须走 `CFLAGS_EXTRA` / `LDFLAGS_EXTRA`。

### 二、★★ 三个「屏上什么都没有」的真凶（都不是"代码没生效"那么简单）
真机现象：**服务看着起来了、日志不喊、屏上纹丝不动**，SPI 每秒仍 +153,611 B。

**真凶① `pgrep -x xwrt-doom` 打中 init 脚本自己**（BusyBox procps 的 comm 语义）
- 真机实测（BusyBox v1.38.0）：`/tmp/xwrt-doom start` ⇒ `pgrep -x xwrt-doom` 返回
  `32175 comm=[xwrt-doom] cmd=[/bin/sh /etc/rc.common /tmp/xwrt-doom start]`。
  换任意 basename 原样复现（对照组 `zzprobe`）⇒ **comm = 脚本 basename**，与文件内容无关。
- 硬断言对照：真 doom(pid 435) + 同名 rc.common 包装(pid 493) 在场时
  `pgrep -x xwrt-doom` ⇒ `435 493`（493 是误报）；`pgrep -f '^/usr/bin/xwrt-doom'` ⇒ `435`（恰好只有真进程）。
- **两个致命后果**：① 状态文件长期说谎（`running=1` 但无进程）；② `kill_doom()` 的 SIGTERM
  **打中正在执行 `start_service` 的那个 shell 自己** → `procd_open_instance` 根本没跑到
  ⇒ "服务说启动了，屏幕上什么都没有"。
- 修复：PID 文件 `/var/run/xwrt-doom.pid` + `pgrep -f '^/usr/bin/xwrt-doom'`，
  PID 复用再用 `/proc/<pid>/cmdline` 复核。

**真凶② procd respawn 把面板 ucode 拉回来占着 DRM master**
- `xwrt-panel` 带 `procd_set_param respawn`（实测 `threshold:3600 timeout:5 retry:5`）
  ⇒ **只要 procd 里 instance 还在，杀 ucode 5 秒后必被拉回**。
- `disable` **只删 `/etc/rc.d/S99xwrt-panel` 软链，不注销已注册实例**；而 `panel.uc` 在 procd
  `term_timeout`（5 s）内不退 ⇒ 日志出现
  `not stopped on SIGTERM, sending SIGKILL instead` ⇒ 手工清场**一律 `kill -9`**。
- ★ 修复 = `panel_stop()` 三步缺一不可：**停服务（注销 procd 实例）→ `kill -9` →
  轮询 `/sys/kernel/debug/dri/0/clients` 确认 master 真空出**。

**真凶③ 面板空转刷新恰好也是「每秒 +153,611 B」** —— SPI 判据把人骗了
- 面板 ucode 占着 master 时 SPI 仍**每秒稳定 +153,611 B**（它自己 1 fps 空转）；
  真 doom 是 **+153,611 × 36/s**。⇒ **"SPI 在涨"不能证明是播放器在推**。
- ⚠️ 且 SPI 计数器是**自开机累计的绝对值** ⇒ 算"本次上了几帧"**必须先减起始快照**。
  忘减会印出 `SPI 累计 <手机号-C> B ⇒ 122100.3 帧 (4686.2 fps)` 这种荒唐数字。

**附带两个**
- `commit 失败: Resource busy` **其实是 EACCES 的误报** —— 失败分支打的是 `errno`，而 `nanosleep()`
  会改掉它 ⇒ 重试循环里必须存 `last_e`。
- `get-wad` 下不动（`certificate is self-signed or not signed by a trusted CA`）：真机证实是
  **全局** TLS 信任链问题（`downloads.openwrt.org` 同样失败，`ca-bundle` 已在）⇒ 三个下载器一律
  加不校验参数 + 固定字节数/md5 双兜底。

### 三、★ 帧率：从 17.43 → 36 fps
- 根因不是 SPI：**Doom 一帧 = 1 game tic = 28.57 ms（35 Hz）**，而 `1/30 = 33.3 ms` 的简单门
  只比它大一点 ⇒ **每次等第 2 个 tic ⇒ 35/2 = 17.5 fps**（实测 17.43）。
- 解法 = **令牌桶**（< 0.85 不放行、允许提前）⇒ 真机 **36.01 fps**。
- 真机验收（10 s 窗口）：Δ = 55,299,960 B ⇒ **360 整帧**，逐秒 9×36 + 1×37；
  26.02 s 样本：`提交 937 帧 / 26.02s = 36.01 fps；本会话 SPI Δ 143933507 B ⇒ 实际推上屏 937.0 帧` ——
  **两条独立计数逐帧吻合**。
- 分项：循环 27.74 ms = 绘制 0.27 + **提交 26.09** + 睡眠 1.008；tic `gametic=872 / 26.02s = 33.5 Hz`
  （35 Hz 的 96%，游戏速度正确）。
- ⚠️ **提交 26.09 ms 就是同步等 SPI 吐完**（153,611 B @52 MHz ≈ 23.6 ms，理论上限 42 fps）
  ⇒ **36 fps 已是物理上限，别再"优化"**。
