## 六、★ WAN↔LAN 路由 + NAT 硬件卸载 —— 已验通（09:30~09:45）

WAN 插线后 `eth1` 通过 DHCP 得到 `192.168.15.109/24`，默认路由 `via 192.168.15.1`；
**`eth1` 协商 2500Mb/s**（对端支持 2.5G ✅）。`lan1/lan2` 只协商 **1000Mb/s**（Windows / Ubuntu 都是 1G 网卡）
⇒ 端到端吞吐上限 ~790 Mbit/s，2.5G 需 LAN 侧换网卡。

### 几何陷阱：同网段双归属主机会"短路"
Windows（14.130 + 15.129/15.177）与 Ubuntu（14.231 + 15.157）**都同时有两侧地址**，
直接打对端 15.x 会被内核判为同网段直连、绕开路由器。
手法：Windows 加 `/32` 路由强制绕行 ——
`route add 192.168.15.157 mask 255.255.255.255 192.168.14.1 metric 1 if 21`，
`tracert -d -h 3` 确认第 1 跳 = `192.168.14.1` ✓。
Ubuntu 侧 `sudo -n` 失败（无免密 sudo）⇒ 改用 **`iperf3 --bidir`** 让 Ubuntu 反向推流，
同样把"WAN→LAN 下行"变成大流量，**无需改任何路由**。测试后已 `route delete` 复原。

### 三级对照（iperf3 穿 MT5000，各 ~2.04 GB）

| 运行状态 | PPE BND | CPU 均值 | CPU 峰值 | 吞吐 |
|---|---|---|---|---|
| **hwnat=1**（硬转开） | **4 条**（4 流全绑） | **0.8 %** | 6 % | 788 Mbit/s |
| **hwnat=0**（软件快速路径） | 0 | **11.1 %** | 13 % | 789 |
| **disabled=1**（natflow 全关） | 0 | **29.5 %** | 33 % | 788 |
| hwnat=1 + `--bidir` | **8 条** | 3.4 % | 25 %\* | 767↑ / 129↓ |

\* 峰值出现在建连瞬间。

### ★ 开关陷阱（踩到了）
`/dev/natflow_ctl` 里读到的 `hwnat=` 是 **uci 配置值**，不是运行态：
先 `echo disabled=1 > /dev/natflow_ctl`，它**仍然显示 `hwnat=1`**，但实测 BND 已掉 0、CPU 翻 4 倍。
⇒ **判"卸载开没开"只能看 PPE 条目**。两级开关：
- `uci set natflow.main.hwnat=0; uci commit natflow; /etc/init.d/natflow-boot restart` → 关硬件卸载（软件快速路径仍在）
- `echo disabled=1 > /dev/natflow_ctl` → natflow 整体关（连软件快速路径也没了）

### ★ PPE 条目证据（hwnat=1，-P 2）
```
00e04 BND IPv4 5T orig=192.168.14.130:60673->192.168.15.157:5201
              new =192.168.15.109:60673->192.168.15.157:5201   ← SNAT 到 WAN IP，端口不变
              eth=94:83:c4:c5:0c:fd->98:03:9b:a1:69:73  etype=0008  vlan=0,0
```
- **`vlan=0,0` 是正确的**：该字段记录的是**入口侧** DSA tag；本场景入口是 `eth1`（普通以太、无 tag）。
  对照 LAN↔LAN（入口是 DSA 口）显示的是 `vlan=3072=0xC00|port0` / `3073=0xC00|port1`。
  出口方向的 tag 由 `ib2` 指令完成，不体现在这个字段。
- 起流后 **1 秒内** BND 即 0→4，无需预热。

**真实上网流量同样被卸载**（同期旁路条目）：
`192.168.14.231 → 221.153.216.56:8081`、`192.168.14.130 → 74.125.250.129:19302`（Google STUN）。

### ★ 回程（WAN→LAN）出口 tag 的验证
`iperf3 --bidir -P 4` ⇒ 8 条连接全部 BND，其中 4 条 RX 连接由 Ubuntu 主动推流
⇒ **338 MB 数据从 `eth1` 进来、从 `lan1` 出去**，TCP 完整、零异常。
若出 `lan1` 的帧缺少正确的 `0xC00|port0` tag，RTL8366UB 在 802.1Q tagger 模式下无法定位端口，
这条流不可能跑满且无重传 ⇒ **出口 tag 设置正确**，`795-11` + `999-0001` 在**路由/NAT 场景**下同样成立。

### 遗留
- **2.5G 端到端带宽**：WAN 侧已是 2.5G，需 LAN 侧 2.5G 网卡才能测（当前 lan1/lan2 均 1G）。
- IPv6 卸载、多 WAN / QoS 场景未测。

## 七、★ openwrt/openwrt#24237 评审意见处理 + 搬进上游仓（09:50~）

### dmtpascoal 的 3 条意见（PR 里他只有 3 条行级评论，2026-09-04）
逐条核对全文见 `BE14000-fixes/MT5000-PR24237-REVIEW-DECISION.md`。

1. **proto id 32 与上游 v7.0 的 `DSA_TAG_PROTO_MXL862_VALUE` 撞车** —— **采纳，已修**。
   我们树里 32「空着」只是 6.18 backport 编号错位（762 把 MXL862 编成 30、760-09 用 31）的**假象**；
   内核一 bump 到 7.x，两个 tagger 共用 32 ⇒ 重复枚举静默编译、两个模块都带别名 `dsa_tag:id-32`、
   `dsa_tag_driver_get_by_id()` 按**链接顺序**返回先注册者（无警告）
   ⇒ **RTL8366UB 的 CPU 口静默拿到 MxL862 的 8 字节 tagger**。定时炸弹，非理论风险。
   复核「改数值安全」：全树 `RTL8366UB_8021Q_VALUE` **0 引用**（只定义不用）；
   795-11 的 `mtk_eth_soc.c` 守卫、`mtk_ppe_offload.c` 的 `case`、tagger 的 `.proto` **全用枚举名**；
   模块别名 `dsa_tag:id-%d` 与数值无关 ⇒ 改成 **200**。
2. **VLAN 1 的 `member/untag` 应为 0（不应经默认 PVID 可达）** —— **不改**。
   属 GL 的上游驱动补丁（795-10），下游改会立刻分叉、以后每次同步都要解冲突；
   真机跑完 LAN↔LAN + WAN↔LAN 各 2 GB，`dmesg` **零** `received untagged frame`
   （该告警就在 CPU 口路径上）⇒ 无复现缺陷。记为跟踪项。
3. **CPU 口应设 `accept_tagged_only`** —— **不改**。驱动已有该原语且 CPU 口初始化处确实没用，
   但 dmtpascoal **自己标为 "Worth confirming on hardware"**：EXT 口的 ACCEPT_TAGGED_ONLY
   是否也会拒绝 priority-tagged (VID 0) 帧，**静态无从确认**（只有 2-bit ACCEPT 寄存器写口，
   无手册）⇒ 方案未定稿，不抄进生产固件。记为**上游待办**。

**附带**（`openwrt-ai` 提的，实质成立）：`795-12` 把 `err_free_dummy` 前移时**删掉了
`mtk_unreg_dev(eth)`** ⇒ `register_netdev()` 失败路径不再注销已注册的 netdev。下次同步上游时检查。

## 九、"WAN→LAN 时 CPU 0% 但负载高"—— 实测：**两个指标其实都极低**（11:05~）

用户提出疑问后实测（新固件、hwnat=1、`192.168.14.1`）：

| 场景 | 4 核 busy | iowait | loadavg (1/5/15) | PPE BND |
|---|---|---|---|---|
| 空载 | 全 0% | 0% | 0.01 / 0.11 / 0.09 | 0 |
| **WAN→LAN 下行 868 Mbit/s**（`iperf3 -R -P 4`） | 全 0% | 0% | **0.00 / 0.10 / 0.08** | **4** |
| 小包 906 Mbit/s（`-l 128`，高 PPS） | 全 0% | 0% | 0.05 / 0.10 / 0.08 | 4 |

⇒ **CPU 与 load 都极低**，且 `top` 显示 `0% usr 0% sys 100% idle 0% io 0% irq 0% sirq`。
**用户说的"负载高"与实测不符** —— 最可能是把 `/proc/loadavg` 的 **第 4 字段 `1/135`**（= 可运行/总任务数）
看成了负载值，或者把 0.0x 的**底噪**当成了"高"。

### 关键概念（回答这个问题的核心）
**load average 不是 CPU 占用率，两者是不同维度**：
- `/proc/stat` 的 CPU% 是**时间维度**：CPU 有多少时间在跑 —— 卸载后数据走 PPE，CPU 真的一点不参与 ⇒ 0%
- load average 是**任务维度**：`可运行(R) + 不可中断睡眠(D)` 的任务数，再取 1/5/15 分钟**指数平均**
  ⇒ 一个任务只跑 1 ms 也会被计入，且**衰减尾巴很长** ⇒ 只要有周期性任务就有**非零底噪**

### 底噪来源（这台机器装得非常多）
`/etc/rc.d/` 里启用的服务：adguardhome、passwall(+server)、sing-box、xray、tailscale、haproxy×2、
ttyd、mwan3、usteer、dawn、miniupnpd、ddns、microsocks、pptpd、urllogger、blockd、fakemesh、cron…
它们各自有定时器/socket 轮询 ⇒ 每次唤醒都短暂抬高 runnable 计数 ⇒ **0.0x 的 load 底噪完全正常**。

### 判"load 是否真有问题"的四个判据（本次实测全部干净）
1. **D 状态进程**（不可中断睡眠）→ `ps -eo stat,pid,comm | awk '$1~/^D/'`，本次为空
2. **iowait 占比**（load 会算进去但 CPU 显示 idle）→ 本次 0%
3. **单核饱和**（4 核平均会掩盖）→ 逐核采，本次 4 核全 0%
4. **load 是否持续 > 核数**（4）→ 本次 0.0x

工具：`_tools/m5k_cpu_load_diag.sh`（每核 CPU / iowait / softirq 按核增量 / D 与 R 进程 / loadavg）。
⚠️ 该脚本必须 BusyBox 兼容（无 `nproc`、`paste`、`bc`）；softirq 的 NET_RX 在空载时就**几乎全压在 CPU2**
（27,653 vs 其他核 ~300），ethernet 中断则**全在 CPU0**（GICv3 229/230）—— 但频率只 ~500-950/s，远未饱和。

### 顺带核实
- **MT5000 内存 = 1024 MiB DDR4**（官方规格，实测 `MemTotal` 988 MB ⇒ 正常，不是 DTS 漏写）
- OpenWrt 论坛里 GL 的 PR 说明写着"**does not support LAN-to-LAN; only WAN-to-LAN**"，
  而我们实测 **LAN↔LAN 是通的**（789 Mbit/s + PPE BND 2）—— 这正是 `795-11` 那个**排除式守卫**改动的价值。

### ★ 追加：真正异常的场景是 **LAN↔LAN**（用户纠正后复测）

WAN→LAN 复测 load 全 0.00；**LAN↔LAN（14.130 ↔ 14.231，`iperf3 -P 4`，788 Mbit/s）才有 0.16~0.18**：

| | load1 | procs_running | procs_blocked | 5 s 内线程 tick 总增量 |
|---|---|---|---|---|
| 空载 | 0.04 | 恒 **1** | 恒 **0** | **7**（tailscaled 3、ubusd 1、ttyd 1…） |
| LAN↔LAN 流量中 | 0.16~0.18 | 恒 **1** | 恒 **0** | **10**（tailscaled 5、sh 2、switch_ports_st 1、natcapd 1、dnsmasq 1） |
| WAN→LAN 下行 | 0.00 | 恒 1 | 恒 0 | — |

**关键推理**：CPU 时间只从 7 → 10 ticks（+0.03 s），**load1 却涨了 0.14** ⇒
load 的上涨**不来自 CPU 消耗**，而是**瞬时 runnable 尖峰**被 1 分钟指数平均放大
（我的逐秒采样抓不到尖峰，因为 `procs_running` 恒 1）。
`procs_running` 恒 1、`procs_blocked` 恒 0 ⇒ **没有任何任务在排队/等待** ⇒ **这不是真实负载**。

**尖峰来源**（两类，都与"CPU 要处理流量"无关）：
1. **x-wrt 的周期性短命脚本**：tick 增量里出现 `switch_ports_status`、`natcapd`、`dnsmasq`（各 +1 tick），
   但 `ps -eo comm` 抓不到、`/etc/crontabs/root` 与 `/etc/cron.d/` 都是空的
   ⇒ 它们是**跑几毫秒就退出**的进程，**空载时同样存在**。
2. **每流首包的慢路径处理**（PPE 绑定前）：TCP 握手、ARP/ND、conntrack 创建 —— 一次性。

**判据**：load 0.18 / 4 核 = 4.5% 利用率，正常。真正该担心的只有：
`load` 持续 > 核数、`procs_blocked` > 0（D 状态）、`iowait` 高、单核 busy 100%。

⚠️ **tick 增量必须按 PID 配对，绝不能按 comm**：kworker 是动态创建/销毁的，
同名不同 PID ⇒ 按名字配对会把"新线程的完整 utime"当成增量
（我最初就是这样算出 `kworker/u16:1 +147 ticks` 的假数据，修正后降到个位数）。
工具：`_tools/m5k_who_load.sh`（BusyBox 兼容）。

### 五条最关键的实测结论
1. **`AT+GTUSBMODE=?` → `(17-18,20-21,24,29-33)`** —— 本机 mode 集合 =

2. **`AT+GTCCINFO?` 是多行带文本标签、且 4 个字段是十六进制**：

3. **慢命令实测（无卡时，端口串行 ⇒ 一条卡死饿死全部）**：

   `AT+GTCCINFO?` 25 ms、`AT+GTUSBMODE?` 16 ms ⇒ **轮询表没被污染**。

### ★★ 上一轮构建其实**失败了**：samba4 4.18.11 vs glibc ≥ 2.39
```
lib/replace/replace.c:973: error: too many arguments to function 'memset_explicit'
  memset_explicit(dest, destsz, ch, count);
```
- samba 的 `rep_memset_s()`（C11 `memset_s(dest,destsz,ch,count)` 的兜底实现）内部调
  `memset_explicit()` **传了 4 个参数**，而 C11/glibc 的原型是 **3 个**，且语义上该写
  `count` 字节而不是 `destsz`。**这是 samba 的真 bug**。
- **为什么现在才炸**：glibc 2.39（Ubuntu 24.04）才新增 `memset_explicit`；此前
  `HAVE_MEMSET_EXPLICIT` 为假、走 `#else` 分支，这行**从未被编译**。⇒ 厂商 CI 用旧
  glibc 编得过，**只有这台机器会踩**。

  ★ **补丁用 `diff` 从 `dl/` 里的原始 tarball 生成**（`tar -xOf` 取出单个文件 → sed 改 →

## 16:25~16:50 · BE14000 开源驱动 MLO 实测 —— **能开，但要绕过 hostapd socket 生命周期 bug**

真机 `192.168.15.1`（BE14000 / X-WRT 26.04_b202609121905 / 内核 6.18.44 / MT7996E）。细节 → `BE14000-fixes/MLO-OPEN-SOURCE-DRIVER.md`。

**结论**：UCI 就能配 MLO（`option mlo '1'` + `option device 'radio0 radio1 radio2'`，空格分隔），
`encryption=sae` 必须（MLO 强制 WPA3）；**LuCI 里没有这个开关**。
整条栈都具备能力，**mt7996e 真的建出了 `ap-mld0` 并进 br-lan**；但默认路径**必然失败**，且会**连带打挂该 phy 自己的 AP**。

**根因（两段）**：
1. 同一次 bring-up 内 `Add MLD interface ap-mld0` 后**立即** `Remove MLD interface ap-mld0`（churn）；
2. ⚠️ **`/usr/share/hostap/common.uc:43` 的 `wdev_remove()` 只发 `NL80211_CMD_DEL_INTERFACE`，
   从不 unlink `/var/run/hostapd/<ifname>`** ⇒ 紧接着的重加撞上
   `ctrl_iface exists and seems to be in use - cannot override it` → `Failed to setup control interface for ap-mld0`，
   并连带 `hostapd.add_iface failed for phy phy0.1/0.2 ifname=phy0.1-ap0/phy0.2-ap0`
   ⇒ `netifd: radio1/radio2 command failed: No such device (-19)`。

**绕过（已实测出 AP MLD）**：bring-up 期间跑 watcher，**只在 `! -e /sys/class/net/ap-mld0` 时**
才 `rm -f /var/run/hostapd/ap-mld0` ⇒ 绝不碰活着的 MLD。成功后：
`iw dev ap-mld0` = `ssid X-WRT_MLO / EHT80 / ch21 6.055 GHz / WPA3 SAE`；
三个 phy conf 各一个 `bss=ap-mld0`、**link BSSID 互不相同**（2.4G `…3f:aa`、5G `92:…:ab`、6G `96:…:ac` = MLD 地址）；
`hostapd.ap-mld0` ubus 对象存在、`Set MLD config: ["ap-mld0"]`、`br-lan` 已挂。

### 本轮新踩到的坑
1. ⚠️ **BusyBox 的 `sleep` 不接受小数**：`sleep 0.1` → `sleep: invalid number`，循环退化成**忙等**，
   瞬间刷出 580 KB 日志并吃掉 CPU。必须用整数秒。

### 本次新增的两条硬结论（重要）
- **`.img.gz` 尾部 860 B 不是损坏，是元数据页脚**：`8×00` + `{"metadata_version":"1.1","compat_version":"1.0"...}`
  + base64 块 + `FWx0` + 长度。`gzip -t` 因此返回 **2**（`decompression OK, trailing garbage ignored`）。
  ⇒ **绝不能用 `gzip -t` 判镜像完整性**；改 `gzip -dc | wc -c` 且只把「非 trailing garbage」的抱怨当错误。
- **`kmod-usb-xhci-hcd` / `kmod-usb2` / `kmod-usb3` / `kmod-usb-ehci` 不在 manifest 里 ≠ USB 坏了**：
  本树 `CONFIG_USB_XHCI_HCD=y` / `_XHCI_PLATFORM=y` / `_EHCI_HCD=y` / `_DWC3=y` 是**内建**（`System.map` 838 个 xhci 符号），
  内建即无 `.ko` 故无包；`CONFIG_USB_SERIAL=m` / `_OPTION=m` / `_WWAN=m` 是模块且都在镜像里。厂商固件是当模块编的，所以那边有这些包。
- **`comm` 比包集合必假**：两侧 `sort` 来自不同机器（busybox vs MSYS），`comm` 的行归并假设崩掉 ⇒ 会把 1117 个包全报成唯一。
  改用 Python 集合差（`_tools/istoreos-h69k/pkgdiff.py`）。
- **Windows 的 `find.exe` 会截走 MSYS `find`**（与 `sort`/`timeout` 同类）：`find … -type f` 静默返回空，`ls -laR` 才是真相。

### 3.5 工具坑（本轮新踩）
- **设备 busybox 没有 `base64` applet、没有 `timeout`** ⇒ 推二进制只能 `scp`（`ash: base64: not found` 让推送死在最后一步）；

  ⇒ 失败分支正确跳过回读。
- 为什么用**单个全非法 token** 而不是 `101,999999`：若模组静默忽略未知码，混合列表
  会只留下 LTE B1，那就**真的改了设置**。单个非法 token 只可能「被拒」或「空」，
  而空列表是我们本来就已经在的那个宽松端。

  ⇒ ★★★ **空字段（`AT+GTACT=,,,`）的语义实测确认为「保留当前值」，不是「复位默认」**。
