## 一、M5 GNSS —— 真机事实采集（用户授权「若 100% 不影响连接性就开机测」）

用户原话：**「如果100%不影响模块连接性，你就开gnss直接测吧。」**
⇒ 所以本轮第一步不是开机，而是**先把这个「100%」证实或证伪**。

### 1.1 ★★ 结论：开 GNSS 对连接性的影响 = 实测 0

三重独立证据，任一单独都不够：

1. **手册特性表**（`GNSS-Application-Guide.txt` §1.1，`AT+GTGPSPOWER`）：
   `Require Restart to Take Effect = **No**` + `Require Data Store at Power Down = **No**`
   + 不需要 SIM/注网/数据连接 + 同步命令（≤500 ms）。
   ⇒ 能伤到连接性的两件事（**重启 UE**、**持久改配置**）手册都明确排除。
2. **结构上不可能重枚举**：设备 `bNumConfigurations = **1**`，
   5 个接口已全部绑定驱动。要加第 6 个口必须换配置 ⇒ 必然重枚举。
   而 mode 17/32 的接口表里根本没有 GNSS 口（见 §1.3）。
3. **当前无 SIM ⇒ 本来就没有「连接」可掉。**

实测对照（`2cb7:0104`，开机前 vs `GTGPSPOWER=1` 之后）：

| 判据 | 前 | 后 |
|---|---|---|
| `bNumConfigurations` / `bConfigurationValue` | 1 / 1 | 1 / 1 |
| `bNumInterfaces` | 5 | 5 |
| 接口集合 | `2-1:1.0 … 1.4` | 同 |
| `/dev/ttyUSB*` | 0,1,2,3 | 0,1,2,3 |
| at-daemon 持有的口 | `/dev/ttyUSB2` | `/dev/ttyUSB2` |
| `event_drop_count` | 0 | 0 |
| AT 面 `AT+CGMI` | 应答 | 应答 |
| 内核日志 USB 事件 | — | **无重枚举 / 无 new device / 无 disconnect** |
| `fm160d` PID | 19037 | **19037** |

关机后逐项回到基线。整轮（开机→5 次 NMEA 读→关机→再开机→计时→关机）
`logread | grep -cE 'signal 11|segfault|crash loop|exit_code'` = **0**。

⚠️ 诚实边界：对未文档化的固件行为无法**先验**证明「100%」。上面是
「文档排除 + 结构不可能 + 实测不变」+ 即时回退（`GTGPSPOWER=0`）
+ 自愈（掉电自动回 0）。据此判定风险可忽略，于是执行。

### 1.2 ★★ NMEA 从 **AT 口**出；本模式下**不存在** GNSS 口

**这是本轮最有价值的一条，因为它决定 M5 的架构。**

GNSS 指南自己的例子就是 `AT+GTGPS?` 直接回 NMEA 段落 ⇒ NMEA 是**命令响应**，
不是独立口上的 URC 流。实测确认。

再查 USB 模式表：`AP(GNSS)` 接口**只出现在 mode 40/41**（`0x7126`/`0x7127`，RNDIS），
而本机是 **mode 17/32**（`0x0104`），接口集只有
`DIAG | Modem | AT | Pipe | RmNet`。实测 tty→接口映射逐项吻合：

| tty | 接口 | 角色 | 端点 |
|---|---|---|---|
| `ttyUSB0` | `2-1:1.0` | DIAG | 2 |
| `ttyUSB1` | `2-1:1.1` | Modem | 3 |
| **`ttyUSB2`** | `2-1:1.2` | **AT** | 3 |
| `ttyUSB3` | `2-1:1.3` | Pipe | 3 |
| — | `2-1:1.4` | RmNet（`qmi_wwan`） | 3 |

⇒ **5 个口里没有任何一个是 GNSS 口。**

**架构结论：M5 不需要 open 新口、不需要 lease、不需要监听 URC。**
走的是已经跑了几万行的 `ttyUSB2` 通道 ⇒ 对「稳定性优先」这个要求是最好的结果。

### 1.3 ★★ 这台机器**没有接 GNSS 天线**（必须写进 UI）

跨 **100 秒**五次采样，响应**逐字节完全相同**（含全部八个校验和），
可见卫星恒 **0**。接天线时 100 秒内至少会看到几颗 ⇒ 判定**射频输入不存在**。

⇒ 后果：**「有定位」形态的 NMEA 在本机无法联调**；
UI 必须能诚实显示「引擎已开 / 0 颗星 / 无定位」，**不能当错误**。

### 1.4 NMEA 原始响应（引擎已开、无定位）

```
\r\n+GTGPS: \r\n
$GPGSA,A,1,,,,,,,,,,,,,,,,*32\r\n      ← 1 = fix not available
$BDGSA,A,1,,,,,,,,,,,,,,,,*23\r\n
$GAGSA,A,1,,,,,,,,,,,,,,,,*23\r\n
$PQGSA,A,1,,,,,,,,,,,,,,,,*24\r\n
$GPGSV,1,1,0,1*54\r\n                  ← 0 颗可见；尾随字段疑似 signalId
$BDGSV,1,1,0,1*45\r\n
$GLGSV,1,1,0,1*48\r\n
$GAGSV,1,1,0,7*43\r\n                  ← 7 = Galileo E1（与 signalId 说自洽）
\r\nOK\r\n
```

三条要点：
* `+GTGPS:` 后**直接换行**，语句在后续行 ⇒ 不能假设值在同一行。
* **只出现 GSA / GSV，没有 RMC / GGA**（无定位时带位置与时间的句子整段省掉）
  ⇒ 判「NMEA 正常」**不能**要求 RMC 存在。
* **0 颗星的 GSV 仍带尾随字段**（标准格式此时无尾随字段）
  ⇒ 解析器要按**字段数**容错，且**校验和必须真算**，不能靠形状判断。

### 1.5 四处语法/行为细节

| 现象 | 原始响应 | 结论 |
|---|---|---|
| `<item>` 不加引号 | `AT+GTGPS=RMC` → `ERROR` | **必须带引号** |
| `<item>` 带引号 | `AT+GTGPS="RMC"` → `+GTGPS: ` 空载荷 | 接受；无定位时为空 |
| 引擎**关**着时读 | `AT+GTGPS?` → `ERROR` | **必须先开机再读**（UI 顺序约束） |
| 开机后**第一次**读 | 载荷 88 B（只有头） | **空帧≠错误**，引擎还在出句子 |
| 开机后第二次起 | 载荷 304 B（8 条语句） | 稳定形态 |

⇒ 构造器发 `AT+GTGPS=<item>` 时**必须自己补双引号**；
daemon 侧「空载荷」要走**与 ERROR 不同**的分支。

### 1.6 成本（决定轮询节奏）

| 调用 | 耗时 |
|---|---|
| `AT+GTGPSPOWER=1` | **50 ms** |
| `AT+GTGPS?`（稳态） | **30 ms** |

⇒ 比 M4 已有的若干轮询还便宜。前景 2–5 s 完全负担得起；建议**只在 GNSS 开着时**轮询
（关着时 `GTGPS?` 只回 ERROR，纯浪费）。`worst_response_ms` 全程停在 117，未被拉动。

### 3.3 ★★ 真缺陷：`AT+GTGPSCFG=?` 是**按字段各有一组取值**，不是一个扁平列表

真机首次拿到应答（**推翻 2.8 的「从未测过」**）：

```
+GTGPSCFG: 0,(0-2)        supl version
+GTGPSCFG: 2,(0-15)       constellation
+GTGPSCFG: 3,(0,1)
（x=1 整行缺失，与 ? 一致）
```

`7c991b5` 的解析器是在「从未见过应答」时写的 ⇒ 把所有括号组**并成一个列表**当写许可。
它今天**恰好正确**——x=2 的集合恰是另两个的超集，并集正好等于它。但它真正在问的是
「这个值对**任意**字段合法吗」。换个固件、让别的字段范围更宽 ⇒ 会放行模组拒绝的写，
而检查**看上去一直在工作**。★ **巧合不是检查。**

**修法**：x 从**行首应答头**读（不能按位置推——x=1 整行缺失，按位置会把 x=3 的集合
挪到 x=2，正是写路径用的那个）；无头的组进独立槽位，**只记录不授权**；
`caps_valid` 现在专指「x=2 的集合已知」。

* 快照：`config_caps.by_x=[{x,values}...]`；`values` **仍是 x=2 集**（不是并集，键义不变）；
  另加 `write_x` / `x_mask`。
* 前端：别的字段的集合**按其本来面目**显示（另一个设置的取值范围），不折进下拉。

## 5. M3 短信（PDU 编解码 / 收发 / 存储 / 长短信）

### 5.1 D4 的「`sendat` prompt 补丁」**作废**

原计划要给 `at-daemon` 的 `sendat` 追加 `prompt`/`payload_hex` 字段。

### 5.2 ★ 短信绝不进轮询表 —— 这一条决定了整个页面的形状

`[实测]`（§8）：`AT+CSQ` **24 ms**；`AT+CMGF?` **5 373 ms** `+CME ERROR: 10`；

### 5.3 ★★ 八个真 bug（单条短信全都看不出来）

| # | 症状 | 根因 |
|---|---|---|
| 1 | 所有拼接短信被当成独立短信、`part` 恒为 0 | `parse_udh()` 从**字节 0** 开始扫 IE，而字节 0 是 **UDHL**（头长度本身） |
| 2 | 第二段起每段少首字符、末段少尾字符 | `plan_segments()` 放不下一个字符时 `text_step()` 已消费其字节，**游标未回退** |
| 3 | UCS2 长短信 `-E2BIG`，段变 **141 octets** | **UDH 填充位只属于 GSM7**；UCS2 是字节流、头已整字节 |
| 4 | 删掉的消息**重启后复活** | 删除只改内存标志；存储是 append-only JSONL ⇒ 必须追加**墓碑行** |
| 5 | 删除中间一条后列表跳号 / 显示已删项 / 顺序乱 | `fm160_sms_get()` 按**环形槽位**倒序取，而删除留洞、新消息写进洞 ⇒ 改为**按 id 排序选取** |
| 6 | 删了本地，模组槽位仍被占着 | 删除必须**两份副本都动**（`AT+CMGD` + 本地），且回复**分开报** |
| 7 | ★ `sms_delete`/`sms_markread` **100% 返回 Invalid argument** | 策略声明 `BLOBMSG_TYPE_INT64`，而 libubox 把**放得进 int32 的 JSON 数字存成 INT32** ⇒ 只接受罕见大值、**拒绝所有小值**。**M4 的 `setcelllock` earfcn 有同一个潜伏 bug**。修法：策略不写 `.type`（UNSPEC）+ `blobmsg_get_u64()` |
| 8 | 无卡时页面显示「还没问完」，把模组原话藏起来 | 前端 banner 先判 `!probed`，而 `probed` 只在 `AT+CPMS?` **解析成功**时才置位 ⇒ 必须**先判 `last_error_text`** |

### 5.5 ⚠️ 意外：`setcelllock` 被我打进了写路径

为验证 5.3-#7 的类型修复，用 `setcelllock` 做了两种数值形状的对照 —— 那**不是**
只测参数解析，命令**真的发出去了**：日志出现 3 次 `cell lock write: AT+GTCELLLOCK=0`。

**影响为零**：命令是 `mode=0` = **关闭**，而模组本来就是 disabled ⇒ **恒等回写**，

**教训**：`ubus call` 打到写方法上，**没有「只测参数解析」这回事**。要测参数形状
用 `20-m4-dryrun.sh` 的干跑（构造器源码编打印器），它一条命令都不发。

## 8.1 ★ 推送成功：那次 token 失效是**暂时性**的，先重测再改道

`git push <URL 内联令牌> main:main` ⇒ `6d461b9..fc9084b  main -> main`；远端
`refs/heads/main` = `fc9084b54db3a315b8533a53063c4c723bd86b11`（= 本地 main，领先 3 提交）。
**教训**：上次同一条命令报 `remote: Invalid username or token.`，这次同一令牌直接成功 ⇒
别急着改走 `git bundle` 绕道，**先用 `git ls-remote <同一个 URL>` 重测一次**；`ls-remote`
通了就说明是瞬时故障（网络/沙箱/GitHub 抖动），不是凭据问题。
⚠️ 内联 URL 推送**不会**更新 `origin/main`（git 不认那个 URL 是 `origin`）⇒ 推完要补一次

# 12. 「无卡只注 LTE 不注 5G？」—— 实测否掉了这个前提

## 12.1 探针与原始值（全程只读，未改模式）

`ubus call fm160 at '{"cmd":"…","timeout":N}'`（走 daemon 串行锁，手动命令自带

落盘成 `/tmp/at-*.sh` 再 `sh` 跑（§0-10：绝不把多行内容穿过 ssh 链）。

```

AT+CFUN?   → +CFUN: 1,0         AT+CGREG?  → +CGREG: 0,2
AT+CSQ     → +CSQ: 24,99        AT+CEREG?  → +CEREG: 0,2
AT+COPS?   → +COPS: 0           AT+C5GREG? → +C5GREG: 0,2
```

## 12.2 ★★ 四条注册域**全是 `stat=2`** ⇒ LTE 与 5G **都注不上**

「没卡只注 LTE」前提不成立。注册 = **NAS 层鉴权**，需 USIM 的 IMSI+K；没有卡，
EPS 与 5GS 同样被拒。**原因与 RAT 无关。**

## 12.3 ★ 真正被误读成「只注 LTE」的是 **AS 层 camped cell**

`AT+GTCCINFO?` 只报 **LTE** 服务小区（电信 46011 · band 105→B5）+ 2 个 LTE 邻区，
**零 NR 行**。⇒ `NAS 未注册` 与 `AS 已驻留` **不矛盾**：限制服务（读广播）不需鉴权。

# 12. 「诊断报告 -32002」+「拨号要单独一个界面」= **同一个根因**（overlay 遮蔽 round 2）

## 12.1 症状 → 真因（一个）

用户报：`无法生成诊断报告: RPCError: RPC call to fm160/diagnostics failed with
error -32002: Access denied`，以及「还有拨号单独做一个界面」。

真因：刷机后 `/overlay/upper` 里**两份 M5 时代的副本**盖住 M6 镜像：

## 12.2 ★★★ `-32002` 的三个层次（每层都能得出反结论）

1. **CLI `ubus call` 永远通过** —— 裸 ubus 连接**没有 session**，ubusd **只对带 session 的连接**
   做 ACL ⇒ **最顺手的那个测试给出的是反结论**（我先按它判断过一轮）。
2. **`ubus call session access` 不是 oracle** —— 旧 ACL 在场时它对 **13 个方法全回「允许」**

3. **只有 HTTP `/ubus` 是真相**：`curl -s -X POST ... http://127.0.0.1/ubus` 逐字复现了
   `{"error":{"code":-32002,"message":"Access denied"}}`；修复后同一调用拿回 4290 B。
   ★ 码对照：`-32000` Object not found / **`-32002` Access denied**。

## 12.3 ★★ `list read '*'` ≠ 「ubus 暴露的一切」

`/etc/config/rpcd` 的 `'*'` 含义是**磁盘上所有 ACL 组** ⇒ 某方法**没有任何 ACL 文件提到**时
**连 root 也被拒**。CLI 通过只是因为不走 ACL、**不是** root 有特权。
⇒ 这才是「管理员自己点得动、别人点不动」的真正机制。

## 12.4 ★★ 基线：旧 ACL 下缺 **6 个**授权，不只 `diagnostics`

  （git 是 Windows 程序，不认 MSYS `/tmp`）⇒ 必须 `C:/…` 形式；`-c credential.helper=`（空值）
  用来禁用已配的 GCM，否则它可能先弹交互框。
* `_tools/` 仍无版本控制；本轮改 `11` 与 `15`，`11` 已落盘构建机。

## 14.8 ★ 附带实证：「沙箱拦 push」这个旧结论要修正

存档 §18 记的是「Windows `git push` 被沙箱拦 ⇒ bundle → Ubuntu 再推」。
本轮查明真因**不是沙箱**，而是 **`git push` 在无 TTY 时挂在凭据提示上**（空输出 + 不返回）。
带 `GIT_ASKPASS` 后**工作站直接推成功**，不需要 bundle 转 Ubuntu。
⇒ 以后先试工作站直推，bundle 只当兜底。
