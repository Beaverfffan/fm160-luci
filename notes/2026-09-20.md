### 2.2 QMI 在 mode 32 下不可用（三条独立证据）

`uqmi -d /dev/cdc-wdm0` 连 `--sync` 都 **`Request timed out`**。逐条排除：

1. **不是绑错**。内核表就是上游意图：
   `option.c:2437` = `USB_DEVICE(0x2cb7, 0x0104)` + `.driver_info = RSVD(4)|RSVD(5)`；
   `qmi_wwan.c:1456` = `QMI_QUIRK_SET_DTR(0x2cb7, 0x0104, 4)`，宏展开 = **`USB_DEVICE_INTERFACE_NUMBER(…,4)`**。
   ⇒ `option` 拿 iface 0–3、`qmi_wwan` 拿 iface 4，**与上游一字不差**。⚠️ 0x0104 是 **NL678 的 PID，FM160 借用了它**。
   ★ **判据**：iface `2-1:1.4` 有 **`ep_88` 中断 IN、maxpacket=8** —— 这是 QMI/WDM 通知端点的指纹
   （`1.1/1.2/1.3` 的中断端点都是 **10** 字节的 CDC 通知）。⇒ **1.4 确实是 QMI 控制面**。
2. **不是 AT 口占用**。停 `fm160d` + `ubus call at-daemon close` 让 AT 口完全安静 ⇒ 仍超时。
3. **不是宿主侧状态**。`unbind`/`bind` `2-1:1.4` 重建 cdc-wdm0 ⇒ 仍超时；`raw_ip=Y` ⇒ 仍超时；
   **身份重写 `AT+GTUSBMODE=32`（强制 USB 重枚举、重建全部 USB 功能）⇒ 仍超时**。

★ **`AT+GTWWAN` 在这个 comp 下两个方向都被拒**：`=1,1` 与 `=0,1` **都回裸 `ERROR`**，
而 `AT+GTWWAN=?` 回 `+GTWWAN: (0,1),(1-23)`（命令被识别）。
⇒ 不是「上下文已激活」的状态问题，是**该命令在 QMI comp 里不适用**。
（`net.h:62` 写着「ECM/**RMNET** 用 +GTWWAN」—— 但 mode 32 这个 comp 拒绝它。）

★ **旧固件（09-18 记录）用的是广和通自己打的 `qmi_wwan_f`、跑 RawIP**（`dmesg`: `work on RawIP mode`, `rx_urb_size = 16384`）；
我们这张镜像用的是**内核原生 `qmi_wwan`**。⇒ **QMI 在这台机器上从未被证明可用**，这是第一次试。

**结论：mode 32 下没有任何可用数据面。要数据面就必须离开 mode 32。**

### 3.3 方法：走 daemon 自己的路，不发裸 AT

`ubus call fm160 setusbmode '{"mode":N}'` —— 因为 `fm160_modesw_apply()` 会在写之前把
**回滚点落进 uci**（此后模块可能消失，没有第二次机会）、开 **60 s 静默窗**、并用身份链本就有的
`AT+GTUSBMODE?` 读回复验。裸写一样能切，但这些一条都拿不到。

★ **`verify_result` 语义（实测）**：`1` = 已确认（成功切换的两个方向都是 1）、`-1` = 失败/回滚、
`0` = 未落定。`state=idle` + `vr=1` ⇒ 被 daemon 身份链与脚本 AT 读**两个独立读者**各自确认。

### 3.6 ★★★ ECM 拨号被堵的根因：**能力探测 ≠ 操作探测**（`AT+GTWWAN` vs `AT+GTRNDIS`）

两个 comp 的 verb 实测（★ **接受模式与 comp 相关，不能一概而论**）：

| comp | `GTWWAN=?` | `GTWWAN?` | `GTWWAN=1,1` | `GTWWAN=0,1` | `GTRNDIS=?` | `GTRNDIS?` | `GTRNDIS=1,1` | `GTRNDIS=0,1` |
|---|---|---|---|---|---|---|---|---|
| **32** QMI | OK `(0,1),(1-23)` | `+GTWWAN: 0` | **ERROR** | **ERROR** | OK `(0,1),(1-23)` | `+GTRNDIS: 0` | **OK** | **OK** |
| **33** ECM | — | `+GTWWAN: 1,1,` | **ERROR** | **OK** | — | `+GTRNDIS: 1,1,` | **ERROR** | **ERROR** |

★ mode 32 下 `AT+GTRNDIS=1,1` → OK 且 `+GTRNDIS?` 回**真地址**
`+GTRNDIS: 1,1,"10.176.133.133,240e:479:1650:13bc:…","218.2.2.2,240e:5a::6666","218.4.4.4,240e:5b::6666"`
（`AT+CGACT?` 亦为 `+CGACT: 1,1`）。

★★ **`dialer.c:531 cb_verb_probe()` 的缺陷**：`if (status == AT_STATUS_OK) st->verb = tried;`
—— 它用 **`AT+<verb>=?`（能力）** 判定，而这个模组**两个 verb 的 `=?` 都被答**（`(0,1),(1-23)`），
于是 verb 被冻在 `GTWWAN`，**回退到 `GTRNDIS` 的分支永远走不到**（`:540` 只在探测**未被答**时才走）。
而 `AT+GTWWAN=1,1` 在 **32 与 33 两个 comp 下都是 ERROR** ⇒ **激活这一步在这台机器上不可能成功**。

★ **后果链**：`dial_start` → `started` → 卡在 `NET_STEP_ACTIVATE` → `dial.up=false` ⇒
`proto_fm160_setup()` 的 `while` 等 `dial.up` 到超时 ⇒ **`usb0` 永远不会被交给 `udhcpc`** ⇒
**产品路径被堵，而底层 comp 明明是好的**（3.5 已证）。
★ 相关文档也反了：`net.h:62` 写「ECM/**RMNET** 用 +GTWWAN，只有 RNDIS 用 +GTRNDIS」——
本机实测恰好相反；且 `net.h:63` 自己承认 dial-up 文档 V1.0 的 ECM 章节用的就是 `AT+GTRNDIS=1,1`。

### 7.2 第一次尝试为什么看起来像死的
- **★ APN 必须走 `--apn` 选项**。`--start-network ctnet ...` 里的裸 `ctnet` **不是报错、是被忽略**
  ⇒ 你会以为「模块不支持」。

### 7.3 ★★ 决定性的硬指标：一个帧都没出去

tx_packets=0  tx_bytes=0  tx_errors=403  rx_packets=0  rx_bytes=0
dmesg: qmi_wwan 2-1:1.4 wwan0: NETDEV WATCHDOG: CPU: 3: transmit queue 0 timed out 5010 ms

⇒ 有公网 DNS、有地址，所以「把地址手工配上网口」看起来应该能通 —— **不通**。

### 7.4 WDS `Start Network` 六种形状全被拒（全 `Invalid operation`）
`apn+ipv4` / `apn+profile 1` / `apn+autoconnect` / 裸 `--start-network`（用默认 profile）/
`--stop-network 0xffffffff --autoconnect` 之后再拨 / 全新 client 不带 `--set-ip-family`。
（唯一一条 `Invalid value` 是**我自己传错**：`--ip-family` 只收 `ipv4|ipv6|unspecified`。）

### 7.5 ★★ 驱动层差异（源码级，两侧绑的是**同一条接口**）
```c
/* 内核 6.6.144  drivers/net/usb/qmi_wwan.c:1456 —— 为 NL678 写的 */

/*   -> .flags = FLAG_WWAN                                  802.3、无聚合、无 QMAP */

/* _ref/fm160/qmodem/driver/fibocom_QMI_WWAN/src/qmi_wwan_f.c:2394 */
{QMI_FIXED_RAWIP_INTF(0x2cb7, 0x0104, 4)}, /* FG150/FM150/NL952/FG101 */
/*   -> .flags = FLAG_WWAN|FLAG_RX_ASSEMBLE|FLAG_NOARP|FLAG_SEND_ZLP|FLAG_MULTI_PACKET

### 8.3 ★★ 本轮最有价值的三个发现
1. **模组自己说它要 raw-IP**：`--wda-get-data-format` →

   **不是保守，是必需的**（mainline 下抄了会让**每帧 RX 静默丢弃**，且看起来像忠实移植）。
2. **新根因**：`AT+GTWWAN?` = **`0`**（ECM/RMNET 数据功能未使能）、`AT+GTWWAN=1,1` = `ERROR`，
   而 `AT+GTRNDIS?` = **`1,1,"10.6.231.190,…"`**（宿主通道绑在 **RNDIS** 上）。
   可是 mode 32 的 USB 布局里**没有 RNDIS 功能**（`1.0..1.3`=option、`1.4`=qmi_wwan）
   ⇒ 模组把宿主数据平面绑到了一个不存在的通道，所以它 ACK 我们的 bulk 传输但不转发任何数据。
   `GTWWAN=1,1` 报 ERROR 的最可能是 cid 1 已被 `GTRNDIS` 占着（同一 cid 互斥）。
3. **判据的源码根据**：`qmi_wan_netdev_ops` 有 `.ndo_get_stats64 = dev_get_tstats64`
   ⇒ `/sys/.../statistics/*` **合并两个计数域**（`dev->stats` + `tstats`）。usbnet 把
   「ACK / URB 报错 / 栈内丢弃」写进**两个不同域**，所以一次要报四个 delta。
   ⚠️ 且 `urb->status==0` 只说明 bulk 传输**被 ACK**，USB 设备可以 ACK 后丢掉载荷
   ⇒ `tx_packets>0` 不能证明模组分帧被解析，**`rx_packets` 才是**。

## 10. 「执行 A」：假设 A 不可执行、假设 B 被实测坐实（47 / 48 / 49，19:00–19:05）

### 10.1 三段的关系

顺带打开一条新路；**49** 用那条新路把假设 B 从推断变成实测。

### 10.2 47：A 的第一步就被拒
```
AT+CGACT=0,1 -> ERROR        cid 1 保持活性（轮询 20 s）
```
脚本**故意中止**（不能拿「起点未变」去测「释放后能否接管」）。回滚里 `AT+CGACT=1,1`
也回 `ERROR` —— **看着吓人但是预期**：cid 已活性时再激活必然 ERROR。现场未变。
**47 的 stage 2（对照）有独立价值**：在 `settle ok after 0s`、控制面全健康的**稳定系统**上，
`--start-network` 仍是 `Call failed` + `data-status: disconnected` ⇒ **上一轮「那是换驱动后的
瞬态」这个开脱被排除**，WDS 失败可复现。

### 10.3 48：先排除混淆项，再下结论
「cid 1 被拒」只有在 `CGACT` 写**能用**时才说明问题 ⇒ stage 1 写一个「不可能有意义」的 cid：
```
AT+CGACT=0,2 -> OK      (cid 2 本就未激活，no-op)
AT+CGACT=1,2 -> OK      CGACT: 2,x 真的变成 1     ← 写路径确实能改状态
AT+CGACT=0,2 -> OK      回 0
```
再摘掉宿主绑定（A 的候选机制）后重试：
```
AT+GTRNDIS=0,1 -> OK    +GTRNDIS: 0
AT+CGACT=0,1   -> ERROR cid 1 仍活性
```
⇒ **同一次运行、同一条 AT 通道、相隔几十秒：cid 2 每条写都服从，cid 1 一条都不服从。**
**cid-specific，不是 binding-specific** ⇒ cid 1 是一个**卡死的会话**。A 不可执行，也不可能是
产品路径（无任何受支持的交出手段）。

### 10.4 48 顺带打开的门
跨 cid 探绑定（为找原因）推翻了「此剖面做不了宿主绑定」：
```
GTRNDIS=1,1 -> ERROR       GTRNDIS=1,3 -> OK  +GTRNDIS: 1,3,"10.206.7.107",…
GTRNDIS=1,5 -> ERROR       GTWWAN=1,1 / =1,3 / =0,3 -> 全 ERROR
```
- **绑定机制是活的**，cid 1 的拒绝只对 cid 1 成立。
- **`AT+GTWWAN` 在此固件惰性**：`=?` 回 `(0,1),(1-23)`（语法被认识），**换 cid 也全 ERROR**
  ⇒ 文档把它标成这个剖面的 ECM/RMNET 词，实为**文档有、固件无**。与 `+GTRNDIS` 一对比，
  结论与厂商文档**正好相反**。

### 10.5 49：换一个**全新 cid**，答案不变 ⇒ B 坐实
cid 1 被这个项目从 45 起反复折腾（raw-IP ping、qmimux ping、释放、重绑、写入）⇒ 必须排除
「测量了被污染的样本」。49 在**从未被碰过的 cid 3**、用**模组刚分配的新地址**、从**干净的
`GTSTATIS` 起点**重测：
```
GTRNDIS=1,3 -> OK   +GTRNDIS: 1,3,"10.200.239.88",…   （每次绑定都换新地址）
CGACT?      -> +CGACT: 3,1        ← 宿主绑定确实激活了 PDP
CGPADDR=3   -> 10.200.239.88      GTSTATIS? -> 0,0,0,0
ip addr add 10.200.239.88/30 dev wwan0 ; ping -c 5 -I wwan0 223.5.5.5
  delta: tx_packets=17  tx_errors=0  rx_packets=0     100% packet loss
  AT+GTSTATIS? -> 0,0,0,0
```
**四次独立测量，换 cid / 换地址 / 换会话 / 换分帧，答案一次都没变：**

| 会话 | cid | 地址 | `tx_packets` Δ | `rx_packets` Δ | 模组 `GTSTATIS` |
|---|---|---|---|---|---|
| 45 纯 raw-IP | 1 | 10.6.231.190 | +24 | **0** | `0,0,0,0` |
| 45 QMAP（`qmimux0`） | 1 | 同上 | +37 | **0** | `0,0,0,0` |
| 46 摘掉绑定后 | 1 | 同上 | +27 | **0** | `0,0,0,0` |
| **49 全新 cid** | **3** | **10.200.239.88** | +17 | **0** | `0,0,0,0` |

⇒ **B 成为实测结论：mode 32（RMNET）在此固件上接收 URB 但不把它们桥进 PDP，与用哪个 cid 无关。**
判据的锋利处：`tx_packets` 只在 `urb->status == 0` 时累加，故 +17 只说明线上被受理；
**`rx_packets` 是 ACK 伪造不了的计数**，四次全 0，模组自己的字节计数也始终为 0。

### 10.6 对 46 结论的修正

```
GTRNDIS=1,3 -> CGACT: 3,1    绑定与激活一起动
GTRNDIS=0,3 -> CGACT: 3,0    再一起回
GTRNDIS=0,1 -> CGACT: 1,1    无效果

### 13.1 ★★ 撤回：`transns` 不是超时计数，是 `carrier_changes`

我在 §12 与存档 §30.6.2 写过「`ip -s -s` 的 `transns 6` = 6 次超时事件」——**错的，现撤回**。定位链（四步互证）：

1. `ip -s -s link show wwan0` 打 `TX errors: aborted 0 fifo 0 window 0 heartbt 0 transns 7`，
   但 `sysfs` 里 `tx_aborted/fifo/window/heartbeat/carrier_errors` **全 0** ⇒ 这个 7 **不来自 `net_device_stats`**。
2. `eth0` 对照：`transns=3`，而 eth0 的 sysfs 也**没有任何字段 = 3**（只有 rx/tx bytes/packets 非零）。
3. `ip -j -s -s`（JSON 带**字段名**）里第二级 TX 唯一非零项是 **`carrier_changes: 7`**；eth0 是 `3`。**两两吻合**。
4. `cat /sys/class/net/wwan0/carrier_changes` = 7、`eth0` = 3 —— 再证一次。

⇒ `transns` 就是 **`carrier_changes`（载波翻转次数）**。那 7 次**全是我们的 down/up 与 `link_state` 写造成的**
（dmesg 末行 `net wwan0: link_state 0x1 -> 0x0` 正是最后那次），与超时无关。

**真实超时事件数 = 1**：`dmesg` 未轮转（首行 `[ 0.000000] Booting Linux…`、共 **930 行**、
末行 uptime 2433 s ⇒ 覆盖整个本次引导），`dmesg | grep -c "NETDEV WATCHDOG"` = **1**（与 `callbacks suppressed` 计数 0 一致）。

**保留的结论不受影响**：`tx_errors` 仍是**延迟计数** —— 超时路径**批量 unlink** 才把它计入，
"发完立即读 Δ0"仍成立；只是"6 次"这个数字作废（改为「≥1 次，实测 1 次」）。

★ **新纪律两条**：①`ip -s -s` 的**人工排版标签**会骗人（`transns`）⇒ **要字段名一律用 `ip -j -s -s`**；
