### 2.3 转折点：原来**必须 power cycle**

- 97 号（重启前、已去掉 `-d`）：udhcpc `broadcasting discover`×3 → **`no lease, failing`**、Δrx=0。

⇒ 结论：**模组的数据通路在多轮失败实验（`$QCRMCALL` NO CARRIER / `+CEER: Regular deactivation` / `NETDEV WATCHDOG`）后卡死，power cycle 清掉了它。** 具体卡在哪一步**未定位**（存档 §33.6 列为第 1 项待收口）。

### 2.4 顺带解开三个长期谜团

## 4. 标准 QMI(uqmi) 复刻 quectel-CM 初始化 —— 取原生 IP、全程不跑 DHCP

用户要求：「我是希望使用标准 qmi 的。请帮我在标准 qmi 复刻 q cm 的初始化机制。
但是最好仍然是拿原生 ip，而不是模块 dhcp 初始化。」→ **已真机验收通过**（细节见存档 §34）。

### 4.1 第一个卡点（也是最大的信息量）

uqmi 一开始**全部查询失败**（`Request timed out`），看着像"模组不支持标准 QMI"。
**是假象**：`/dev/cdc-wdm0` 是**单 reader** 设备，quectel-CM 的 `QmiWwanThread` 在读它。
停掉 CM ⇒ 持有者 0 ⇒ uqmi 立刻全通（37 个服务）。
⇒ **纪律：要动 cdc-wdm0 的标准 QMI 工具，必须先停 quectel-CM。**

### 4.2 复刻成功与判据

映射：`--bind-mux 129 --endpoint-type hsusb --endpoint-iface 4`（TLV 与 CM 逐字段相同）
→ `--start-network --apn ctnet --ip-family ipv4`（PDH 475862496）
→ `--get-data-status` = `connected`
→ **`--get-current-settings` 取原生 IP**（10.25.135.157/30、gw .158、dns 218.2.2.2/218.4.4.4）
→ 静态 `ip addr replace` + `ip route replace default ... metric 11`。
验收：**ping 10/10、0% loss、avg 37.817 ms**；`GTSTATIS=45,0,44239,66722`；
**udhcpc 只剩 eth0 那一个 ⇒ wwan0 上零 DHCP**；eth0 metric 10 主 / wwan0 metric 11 备。

### 4.3 两个坑

1. **`ifdown 2_1` 会把 wwan0 置成管理性 DOWN** ⇒ 没有 connected 路由 ⇒
   路由加不上、ping 报 `Network unreachable`，**看起来像「QMI 没拨通」，其实是二层没抬**。
   修法：`ifdown` 之后显式 `ip link set wwan0 up`。（第一次 `up` 就栽在这。）
2. **`uqmi --start-network` 打印的 PDH 是裸数字**（不是 `"pdh":` JSON）⇒ 取整行纯数字的最后一行。
   解析错会让 `down` 静默跳过 `--stop-network`。
   （同一命令族里 `--get-current-settings` 反而是标准 JSON 表格。）

### 4.4 唯一不可复刻的一步（如实标注）

CM 发的是 **WDS 0x0020 `ADMIN_SET_DATA_FORMAT`**（带 ep TLV），uqmi 只有 **WDA** 版本且 CLI 不填 ep
⇒ 硬照搬会发出「聚合=DISABLED」把 QMAP 关掉。**故 `107` 对它只读不写**，靠"模组侧现值已是
`raw-ip + qmap`（与 CM 的 `qmap_settings.*` 逐字段吻合）"成立。
缺口是真的（uqmi 无 `--wds-set-data-format`），**「该值能否跨模组重启保持」未验证**。
好消息：`qmi-message-wda.h` 的请求结构体**本来就有 `endpoint_info` 字段**，只是 CLI 不填

### 7.1 ★★★★★ 5G 注网：**注上 5G SA，且数据面打通**

**先纠正一个认知错误（本轮最重要的一条方法论）**：上一轮我据一次观测（`+COPS act=7`、
`+C5GREG: 0,0`）写下「无 NR 覆盖」——**这是把「当时的驻留网络」当成了「设备能力」**。
本轮 reboot 后同一台设备、同一张卡：

| 判据 | 命令 | 本轮值 | 含义 |
|---|---|---|---|
| 接入技术 | `AT+COPS?` | `0,0,"????",11` | **act=11 = NR connected to 5GCN ⇒ 5G SA** |
| 5GS 注册态 | `AT+C5GREG?` | `0,1` | **已注册** |
| 服务系统 | `uqmi --get-serving-system` | `radio_interface:["5gnr"]`、plmn 460/11 | 驻留在 NR |
| 系统信息 | `uqmi --get-system-info` | **`5gnr.service_status:"available"`**（lte/wcdma 均 `none`） | NR 可用 |

⇒ **判据纪律：能力查 `GTACT?`/`--get-capabilities`；「现在注没注上」查 `COPS act` + `C5GREG` + `--get-system-info`。两者绝不可互相代替。**

**数据面同时打通**（生产路径，`153`）：
`ping` **6/6 0% loss**、`wget` rc=0 下载 **40 MB**、模块侧 `AT+GTSTATIS?` **+61.5 MB**、
宿主 `wwan0 tx_errors=0`。⇒ 不是「注册上但过不了包」，是**端到端可用**。

### 7.2 ★★★★★ QMI「偶发超时」的真机理（**定论，不是超时**）

**一句话**：不是超时、不是服务未就绪，而是**单次 QMI 请求级的偶发失败** ——
任何一次 uqmi 调用都有小概率拿到 `Failed to connect to service`（CTL 分配 client id 失败）
或 `Unknown error`（模组回了一个 uqmi 不认识的错误码）；**下一次同样的调用立刻就好**，
且**失败落在哪个服务上是随机的**。

| 实验 | 做法 | 结果 | 否证了什么 |
|---|---|---|---|
| **136** | 稳态长跑，失败指纹 | 固定 = `nas=6040ms/TIMEOUT`（吃满 6 s）+ `ctl=40ms/UNKNOWN` + `wds=20ms/ok`；失败间隔 **62.97 s**（另一轮 **65.76 s**） | 证明是**请求级**而非链路级 |
| **138** | 三模式轮转：X=`--get-versions`→NAS；Y=NAS 单独；Z=NAS→NAS | **X/Y/Z 各 40 帧、失败三个模式都有** | **否证**「`--get-versions` 把 NAS 打进忙态」 |
| **135** | `nas TO=20000` 300 次 | min=80 **avg=87 max=110 ms**、`slow(≥500ms)=0`、**0 失败** | **否证**「慢响应/服务忙」 |
| **128** | 单进程 / 双进程 / 双进程+`flock` 各 40–80 次 | **全 0 失败** | **否证**「多 reader 争用」 |
| **138 终局** | 123 帧覆盖 uptime 53→672 s | 6 次失败**全在 uptime ≤152 s**；此后 **515 s / 103 帧 / ~309 次调用零失败** | 失败集中在**开机后窗口** |

**失败率量化**：开机后 0–200 s ≈ **1.8%**（6/330）；稳态 **<0.17%**（0/590，
二项下界可信度 `0.982^590 ≈ 2×10⁻⁵`）。
**最直接的取证**（138）：`t=63.20 nas=240ms/UNKNOWN nas2=80ms/ok`；
`t=89.42 nas=50ms/NOCONN wds=50ms/ok`；`t=151.72 nas=110ms/ok wds=20ms/UNKNOWN`
——**同一个 tick 里前一次失败、后一次成功**，锁死「请求级偶发」。

**⇒ 三条实现要求（已全部落地）**：① `qretry`（对 `Failed to connect to service`/`Unknown error`/
`Request timed out`/`No effect` 重试）；② 就绪门**只问 WDS**（不问 NAS，NAS 在开机窗口最不稳）；
③ 冷启动预算给足 **240 s**（实测 65–110 s 完成）。

**★★ 附带发现：client id 会「语义失效」**。模组经大量会话起停后，`--get-client-id` 会返回一个
**记在账上但其实已无效**的 id（测得 14）：此后每条 `--set-client-id wds,14` 都报 `Unknown error`，
连 `--start-network` 都失败。**修法 = 先 `--sync` 再重新分配**（重取到 17）⇒ 同一串命令立刻全绿。
⇒ 缓存 CID 必须带「失效即 `--sync` 后重取」的自愈。

### 7.3 IPv6：**模组单次会话只给一个 IP 族**，「双栈 = 两路 PDN」

四变体对照（`137/137b`，真机）：

| `--ip-family` 取值 | 模组实际回 | 结果 |
|---|---|---|
| 不传 | `"ip-family":"ipv6"` | **v6-only** |
| `ipv4` | `ipv4` | v4-only |
| `ipv6` | `ipv6` | v6-only |
| `unspecified` | `"ip-family":"ipv6"` | **v6-only**（陷阱：名字像"随便"，实为 v6） |

⇒ 「期望一次拿到双栈」**是错的**（已在代码注释里订正）。默认取 `ipv4` 保底；
要 v6 单栈设 `ipfam=ipv6`；**要双栈必须两路 PDN**（见 §7.5，未走通）。
v6 生产路径端到端通：地址 `240e:479:1650:2118:8ce2:7502:b2c3:e8dc/64`、
`ping6 240e:5a::6666` = **26.7 ms**、`ping6 240c::6666` = **202 ms**（跨 AS）。

### 7.4 ★★★★★ 打包 ipk：真根因是**外层容器格式**（gzip+tar，**不是 ar**）

症状：自研 `.ipk` 装机恒报 `pkg_init_from_file: Malformed package file`，而**我们自己的自检器全过**
⇒ 又一次「判据写错」（自检器校验的格式 ≠ opkg 接受的格式）。

排查链（每步都留了对照）：
1. **排除传输**：两侧 `md5sum` 一致 ⇒ 不是拷贝问题。
2. **对照实验（换成员名尾 `/` 为空格）**：**仍被拒** ⇒ 与斜杠无关，排除一个假说。
3. **下官方真包逐字节对照**：`opkg download zlib` → `/tmp/zlib_1.3.1-r1_aarch64_generic.ipk`（45,548 B）
   `head -c 8` → **`1f 8b 08 00 00 00 00 00`（gzip magic）**，解压后是 **tar**，
   首成员 `./debian-binary`（GNU ustar，`"ustar  \0"`），随后 `./control.tar.gz`、`./data.tar.gz`。

**定论**：本机 opkg（`38eccbb1fd694d4798ac1baf88f9ba83d1eac616`，2024-10-16，24.10 线）
**只吃「外层 gzip+tar」的 ipk，不认 ar**。官方包 = `gzip(tar( ./debian-binary, ./control.tar.gz, ./data.tar.gz ))`
（**嵌套归档**，opkg 靠 libarchive 嵌套打开）。

**修法**：`140-build-ipk.py` 新增 `make_outer_targz()`（GNU tar + `gzip(filename="", mtime=0)` 保证可复现），
`--format {targz,ar}` **默认 targz**；`141-verify-ipk.py` 主判据改为 targz + **校验成员顺序** +
`debian-binary == b"2.0\n"`。

**真机验收通过**：`Installing fm160-qmi (1.0.2-1) to root...` → postinst 引导 → `Configuring fm160-qmi.`；
`opkg list-installed` → `fm160-qmi - 1.0.2-1`。产物 `dist/fm160-qmi_1.0.2-1_all.ipk`（18,174 B）。

### 7.5 数据面真前提 = **power cycle**；★★ 且 `rmmod/insmod` 本身就打死数据面

在 5G SA 上**再次独立复现**了 §33 的卡死形态：dial 全绿（`data-status=connected`、聚合 `qmap`、
地址+DNS 都对、`link_state=0x1`、`carrier=1`），但 **ping 100% loss、`rx_bytes=0`、
模块侧 `AT+GTSTATIS?` 恒 `0,0,0,0`、`wwan0 tx_packets=0 / tx_errors` 随发包数同步 +N**
⇒ **USB TX URB 全部失败**。**只有整机 `reboot` 能清掉。**

★ **本轮新发现（比 §33 更狠）**：`rmmod` + `insmod qmi_wwan_f` **这个动作本身**就会把数据通路打死。
⇒ **要换 `qmap_mode`，正确姿势是 reboot，不是 reload**（`ensure_qmap_mode()` 里的 reload 分支
已加注释警告；已是正确值时直接跳过 reload）。

### 7.6 `qmap_mode` 必须为 **1**（静默失败陷阱）

`qmi_wwan_f.c:2445-2447`：
```c
if (pQmapDev->qmap_mode == 1) pQmapDev->mpQmapNetDev[0] = dev->net;   // 基网卡 wwan0 即数据口
else if (qmap_mode > 1)     for (i=0;i<qmap_mode;i++) qmap_register_device(pQmapDev, i);
```
⇒ `mode==1` 时 **`wwan0` 就是 mux 0 数据口**（139 成功形态）；
`mode>1` 时 RX 只投到 `wwan0.N`，而地址/发送门/健康检查全挂在 `wwan0` 上 ⇒ **静默失败**
（不报错，只是 rx 恒 0）。`/etc/modules.d/82-qmi_wwan_f` 不带参数、**开机实测为 1**
（早先读到 2 是历史残留）。已加 `ensure_qmap_mode()` 自愈 + `status` 里显示该值。

### 7.7 ★ 多路 PDN：**未走通**（撤回早先"已打通"）

- **做法修正（重要）**：`QMIWDS_BIND_MUX_DATA_PORT` **按 client 生效**。`150` 用**同一个 client**
  连做两次 `bind-mux(129/130)+start-network` ⇒ **两次回同一 PDH `1012619552`**，第二路把第一路顶掉。
  正确形态 = **每路一个 WDS client**（`154`：`cid#1=14` / `cid#2=15`，PDH 不同）。
- **第一道坎**：第二路 `start-network` 直接 `"Call failed"`（ctnet 与 ctwap 都试）。
- **第二道坎**：`qmap_mode>1` 数据面本身不工作（`wwan0.1` tx 涨、**rx 恒 0**、base `tx_errors` 同步涨、
  **`GTSTATIS` 恒 0**）⇒ 包根本没到模组。
- 驱动位图/分流（已核对源码）：`link_state` 是**位图**（`offset_id=(v&0x7F)-1`、`v&0x80`=关闭）
  ⇒ 写 `1` 再写 `2`（0x1→**0x3**）；RX `mux_id = qhdr->mux_id - 0x81` ⇒ `0x81→wwan0.1`、`0x82→wwan0.2`；
  `qmap_open()` 要求**基网卡 `wwan0` 先 UP**；`rx_fixup` 恒回 0 ⇒ usbnet 记 1 个 `rx_errors`（**已知良性假象**）。
- **后续方向**：`use_rmnet_usb=1`、`AT+GTRMNETMAP`/`GTMAPNET` 映射、按帧级 `dev_queue_xmit`
  返回码定位 base `tx_fixup` 的 `drop_skb` 分支。
