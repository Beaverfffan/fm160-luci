### 2.3 转折点：原来**必须 power cycle**

- 97 号（重启前、已去掉 `-d`）：udhcpc `broadcasting discover`×3 → **`no lease, failing`**、Δrx=0。

## 4. 标准 QMI(uqmi) 复刻 quectel-CM 初始化 —— 取原生 IP、全程不跑 DHCP

用户要求：「我是希望使用标准 qmi 的。请帮我在标准 qmi 复刻 q cm 的初始化机制。
但是最好仍然是拿原生 ip，而不是模块 dhcp 初始化。」→ **已真机验收通过**（细节见存档 §34）。

### 4.1 第一个卡点（也是最大的信息量）

uqmi 一开始**全部查询失败**（`Request timed out`），看着像"模组不支持标准 QMI"。
**是假象**：`/dev/cdc-wdm0` 是**单 reader** 设备，quectel-CM 的 `QmiWwanThread` 在读它。
停掉 CM ⇒ 持有者 0 ⇒ uqmi 立刻全通（37 个服务）。
⇒ **纪律：要动 cdc-wdm0 的标准 QMI 工具，必须先停 quectel-CM。**

### 4.2 复刻成功与判据

映射：`--bind-mux 129 --endpoint-type hsusb --endpoint-iface 4`（TLV 与 CM 逐字段相同）
→ `--start-network --apn ctnet --ip-family ipv4`（PDH 475862496）
→ `--get-data-status` = `connected`
→ **`--get-current-settings` 取原生 IP**（10.25.135.157/30、gw .158、dns 218.2.2.2/218.4.4.4）
→ 静态 `ip addr replace` + `ip route replace default ... metric 11`。
验收：**ping 10/10、0% loss、avg 37.817 ms**；`GTSTATIS=45,0,44239,66722`；
**udhcpc 只剩 eth0 那一个 ⇒ wwan0 上零 DHCP**；eth0 metric 10 主 / wwan0 metric 11 备。

### 4.3 两个坑

1. **`ifdown 2_1` 会把 wwan0 置成管理性 DOWN** ⇒ 没有 connected 路由 ⇒
   路由加不上、ping 报 `Network unreachable`，**看起来像「QMI 没拨通」，其实是二层没抬**。
   修法：`ifdown` 之后显式 `ip link set wwan0 up`。（第一次 `up` 就栽在这。）
2. **`uqmi --start-network` 打印的 PDH 是裸数字**（不是 `"pdh":` JSON）⇒ 取整行纯数字的最后一行。
   解析错会让 `down` 静默跳过 `--stop-network`。
   （同一命令族里 `--get-current-settings` 反而是标准 JSON 表格。）

### 4.4 唯一不可复刻的一步（如实标注）

CM 发的是 **WDS 0x0020 `ADMIN_SET_DATA_FORMAT`**（带 ep TLV），uqmi 只有 **WDA** 版本且 CLI 不填 ep
⇒ 硬照搬会发出「聚合=DISABLED」把 QMAP 关掉。**故 `107` 对它只读不写**，靠"模组侧现值已是
`raw-ip + qmap`（与 CM 的 `qmap_settings.*` 逐字段吻合）"成立。
缺口是真的（uqmi 无 `--wds-set-data-format`），**「该值能否跨模组重启保持」未验证**。
好消息：`qmi-message-wda.h` 的请求结构体**本来就有 `endpoint_info` 字段**，只是 CLI 不填

### 7.1 ★★★★★ 5G 注网：**注上 5G SA，且数据面打通**

本轮 reboot 后同一台设备、同一张卡：

| 判据 | 命令 | 本轮值 | 含义 |
|---|---|---|---|
| 接入技术 | `AT+COPS?` | `0,0,"????",11` | **act=11 = NR connected to 5GCN ⇒ 5G SA** |
| 5GS 注册态 | `AT+C5GREG?` | `0,1` | **已注册** |
| 服务系统 | `uqmi --get-serving-system` | `radio_interface:["5gnr"]`、plmn 460/11 | 驻留在 NR |

**数据面同时打通**（生产路径，`153`）：
`ping` **6/6 0% loss**、`wget` rc=0 下载 **40 MB**、模块侧 `AT+GTSTATIS?` **+61.5 MB**、
宿主 `wwan0 tx_errors=0`。⇒ 不是「注册上但过不了包」，是**端到端可用**。

### 7.2 ★★★★★ QMI「偶发超时」的真机理（**定论，不是超时**）

**一句话**：不是超时、不是服务未就绪，而是**单次 QMI 请求级的偶发失败** ——
任何一次 uqmi 调用都有小概率拿到 `Failed to connect to service`（CTL 分配 client id 失败）
或 `Unknown error`（模组回了一个 uqmi 不认识的错误码）；**下一次同样的调用立刻就好**，
且**失败落在哪个服务上是随机的**。

| 实验 | 做法 | 结果 | 否证了什么 |
|---|---|---|---|
| **136** | 稳态长跑，失败指纹 | 固定 = `nas=6040ms/TIMEOUT`（吃满 6 s）+ `ctl=40ms/UNKNOWN` + `wds=20ms/ok`；失败间隔 **62.97 s**（另一轮 **65.76 s**） | 证明是**请求级**而非链路级 |
| **138** | 三模式轮转：X=`--get-versions`→NAS；Y=NAS 单独；Z=NAS→NAS | **X/Y/Z 各 40 帧、失败三个模式都有** | **否证**「`--get-versions` 把 NAS 打进忙态」 |
| **135** | `nas TO=20000` 300 次 | min=80 **avg=87 max=110 ms**、`slow(≥500ms)=0`、**0 失败** | **否证**「慢响应/服务忙」 |
| **128** | 单进程 / 双进程 / 双进程+`flock` 各 40–80 次 | **全 0 失败** | **否证**「多 reader 争用」 |
| **138 终局** | 123 帧覆盖 uptime 53→672 s | 6 次失败**全在 uptime ≤152 s**；此后 **515 s / 103 帧 / ~309 次调用零失败** | 失败集中在**开机后窗口** |

**失败率量化**：开机后 0–200 s ≈ **1.8%**（6/330）；稳态 **<0.17%**（0/590，
二项下界可信度 `0.982^590 ≈ 2×10⁻⁵`）。
**最直接的取证**（138）：`t=63.20 nas=240ms/UNKNOWN nas2=80ms/ok`；
`t=89.42 nas=50ms/NOCONN wds=50ms/ok`；`t=151.72 nas=110ms/ok wds=20ms/UNKNOWN`
——**同一个 tick 里前一次失败、后一次成功**，锁死「请求级偶发」。

**⇒ 三条实现要求（已全部落地）**：① `qretry`（对 `Failed to connect to service`/`Unknown error`/
`Request timed out`/`No effect` 重试）；② 就绪门**只问 WDS**（不问 NAS，NAS 在开机窗口最不稳）；
③ 冷启动预算给足 **240 s**（实测 65–110 s 完成）。

**★★ 附带发现：client id 会「语义失效」**。模组经大量会话起停后，`--get-client-id` 会返回一个
**记在账上但其实已无效**的 id（测得 14）：此后每条 `--set-client-id wds,14` 都报 `Unknown error`，
连 `--start-network` 都失败。**修法 = 先 `--sync` 再重新分配**（重取到 17）⇒ 同一串命令立刻全绿。
⇒ 缓存 CID 必须带「失效即 `--sync` 后重取」的自愈。

### 7.3 IPv6：**模组单次会话只给一个 IP 族**，「双栈 = 两路 PDN」

四变体对照（`137/137b`，真机）：

| `--ip-family` 取值 | 模组实际回 | 结果 |
|---|---|---|
| 不传 | `"ip-family":"ipv6"` | **v6-only** |
| `ipv4` | `ipv4` | v4-only |
| `ipv6` | `ipv6` | v6-only |
| `unspecified` | `"ip-family":"ipv6"` | **v6-only**（陷阱：名字像"随便"，实为 v6） |

⇒ 「期望一次拿到双栈」**是错的**（已在代码注释里订正）。默认取 `ipv4` 保底；
要 v6 单栈设 `ipfam=ipv6`；**要双栈必须两路 PDN**（见 §7.5，未走通）。
v6 生产路径端到端通：地址 `240e:479:1650:2118:8ce2:7502:b2c3:e8dc/64`、
`ping6 240e:5a::6666` = **26.7 ms**、`ping6 240c::6666` = **202 ms**（跨 AS）。

### 7.4 ★★★★★ 打包 ipk：真根因是**外层容器格式**（gzip+tar，**不是 ar**）

症状：自研 `.ipk` 装机恒报 `pkg_init_from_file: Malformed package file`，而**我们自己的自检器全过**
⇒ 又一次「判据写错」（自检器校验的格式 ≠ opkg 接受的格式）。

排查链（每步都留了对照）：
1. **排除传输**：两侧 `md5sum` 一致 ⇒ 不是拷贝问题。
2. **对照实验（换成员名尾 `/` 为空格）**：**仍被拒** ⇒ 与斜杠无关，排除一个假说。
3. **下官方真包逐字节对照**：`opkg download zlib` → `/tmp/zlib_1.3.1-r1_aarch64_generic.ipk`（45,548 B）
   `head -c 8` → **`1f 8b 08 00 00 00 00 00`（gzip magic）**，解压后是 **tar**，
   首成员 `./debian-binary`（GNU ustar，`"ustar  \0"`），随后 `./control.tar.gz`、`./data.tar.gz`。

**定论**：本机 opkg（`38eccbb1fd694d4798ac1baf88f9ba83d1eac616`，2024-10-16，24.10 线）
**只吃「外层 gzip+tar」的 ipk，不认 ar**。官方包 = `gzip(tar( ./debian-binary, ./control.tar.gz, ./data.tar.gz ))`
（**嵌套归档**，opkg 靠 libarchive 嵌套打开）。

**修法**：`140-build-ipk.py` 新增 `make_outer_targz()`（GNU tar + `gzip(filename="", mtime=0)` 保证可复现），
`--format {targz,ar}` **默认 targz**；`141-verify-ipk.py` 主判据改为 targz + **校验成员顺序** +
`debian-binary == b"2.0\n"`。

**真机验收通过**：`Installing fm160-qmi (1.0.2-1) to root...` → postinst 引导 → `Configuring fm160-qmi.`；
`opkg list-installed` → `fm160-qmi - 1.0.2-1`。产物 `dist/fm160-qmi_1.0.2-1_all.ipk`（18,174 B）。

### 7.5 数据面真前提 = **power cycle**；★★ 且 `rmmod/insmod` 本身就打死数据面

在 5G SA 上**再次独立复现**了 §33 的卡死形态：dial 全绿（`data-status=connected`、聚合 `qmap`、
地址+DNS 都对、`link_state=0x1`、`carrier=1`），但 **ping 100% loss、`rx_bytes=0`、
模块侧 `AT+GTSTATIS?` 恒 `0,0,0,0`、`wwan0 tx_packets=0 / tx_errors` 随发包数同步 +N**
⇒ **USB TX URB 全部失败**。**只有整机 `reboot` 能清掉。**

★ **本轮新发现（比 §33 更狠）**：`rmmod` + `insmod qmi_wwan_f` **这个动作本身**就会把数据通路打死。
⇒ **要换 `qmap_mode`，正确姿势是 reboot，不是 reload**（`ensure_qmap_mode()` 里的 reload 分支
已加注释警告；已是正确值时直接跳过 reload）。

### 7.6 `qmap_mode` 必须为 **1**（静默失败陷阱）

`qmi_wwan_f.c:2445-2447`：
```c
if (pQmapDev->qmap_mode == 1) pQmapDev->mpQmapNetDev[0] = dev->net;   // 基网卡 wwan0 即数据口
else if (qmap_mode > 1)     for (i=0;i<qmap_mode;i++) qmap_register_device(pQmapDev, i);
```
⇒ `mode==1` 时 **`wwan0` 就是 mux 0 数据口**（139 成功形态）；
`mode>1` 时 RX 只投到 `wwan0.N`，而地址/发送门/健康检查全挂在 `wwan0` 上 ⇒ **静默失败**
（不报错，只是 rx 恒 0）。`/etc/modules.d/82-qmi_wwan_f` 不带参数、**开机实测为 1**
（早先读到 2 是历史残留）。已加 `ensure_qmap_mode()` 自愈 + `status` 里显示该值。

### 7.7 ★ 多路 PDN：**未走通**（撤回早先"已打通"）

- **做法修正（重要）**：`QMIWDS_BIND_MUX_DATA_PORT` **按 client 生效**。`150` 用**同一个 client**
  连做两次 `bind-mux(129/130)+start-network` ⇒ **两次回同一 PDH `1012619552`**，第二路把第一路顶掉。
  正确形态 = **每路一个 WDS client**（`154`：`cid#1=14` / `cid#2=15`，PDH 不同）。
- **第一道坎**：第二路 `start-network` 直接 `"Call failed"`（ctnet 与 ctwap 都试）。

  **`GTSTATIS` 恒 0**）⇒ 包根本没到模组。

## §9 ★★★★★ ECM 剖面（`GTUSBMODE 33`）——「`AT+GTWWAN=1,1 refused`」是假失败（同日追加）

> 用户指令原文：「最近错误: AT+GTWWAN=1,1 refused: AT+GTWWAN=1,1 / 我切换了ecm模式但拨号拨不上，先调ecm」

### 9.1 ★ 一句话结论

**「拨不上」不是拨不上。** 模组在 ECM 剖面上**自己就把 PDP 上下文激活了**，
而宿主侧**从来没有人去拉起 `usb0`**（`usb0` 无地址、无路由、无人 udhcpc）。
页面/日志里的 `refused` 是 **fm160d 的两个代码缺陷**造出来的**假失败**：

> **写入被拒 ≠ 链路没通。读回才是判决，永不是写入的状态码。**

这是本轮唯一的、也是最贵的教训。它**不是**从手册推的，而是**真机实测**出来的。

### 9.2 剖面 = USB 描述符（`GTUSBMODE 33` ⇒ `2cb7:0105`，6 接口）

| 接口 | class/sub/proto | 驱动 | 节点 |
|---|---|---|---|
| `2-1:1.0` | `ff/ff/30` | option | `ttyUSB0`（DIAG） |
| `2-1:1.1` | `ff/ff/40` | option | `ttyUSB1`（答 AT） |
| `2-1:1.2` | `ff/ff/40` | option | `ttyUSB2`（答 AT） |
| `2-1:1.3` | `ff/00/40` | option | `ttyUSB3`（**只回显，不解释**） |
| `2-1:1.4` | `02/06/00` | **cdc_ether** | **`usb0`** ← ECM 数据口 |
| `2-1:1.5` | `0a/00/00` | cdc_ether | 无 netdev |

对照官方《QMI_WWAN驱动集成及拨号指南_CN_V2.3》P9–10：**`GTUSBMODE 33 = DIAG+MODEM+AT+PIPE+ECM+ECM（pid 0105）`逐字段吻合**。

### 9.6 ★★★ 根因：`refused` 是 fm160d 两个缺陷造出来的

**(1) `dialer.c:579-586` `cb_activate()` —— 拒绝即判死**

只对 `AT_STATUS_TIMEOUT` 放行到 `NET_STEP_IP` 去读回；
对 `status != AT_STATUS_OK`（即 refused / ERROR）**直接 `dial_fail("the activation was refused")`**。
⇒ 页面显示该英文，状态 `step=8 (failed)`。

★ **而仓库自己的 `net.h:65-84` 早就实测记下了相反的事实**：
> 「profile 33 (ECM) `+GTWWAN=1,1` REFUSED, `+GTRNDIS=1,1` REFUSED too, ...and the ECM data plane
> was carrying traffic anyway」
> 「a refusal of the write is not proof that the context is down: the module is allowed to have
> activated it on its own, which is exactly what profile 33 does. **The read-back is the verdict,
> never the write's status.**」

⇒ **结论就写在自己的头文件里，代码却在违反它。**

**(2) `net.c` 地址扫描 —— 引号字段里的 v4/v6 对，把 `has_addr` 判死**

`csv_field()` **是认引号的**（引号内的逗号**不切分**）。真机那行被切成 **5 个字段**：

```text
raw_n = 5
raw[0]=1  raw[1]=1  raw[2]="<v4>,<v6>"  raw[3]="<v4>,<v6>"  raw[4]="<v4>,<v6>"
```

对照手册 `?` 句法 `<state>,<cid>,<ip>,<pdns>,<sdns>` ⇒ **`raw[2]` 就是地址**，
但它是 **v4 与 v6 挤在同一个引号字段**里的一对。整串交给 `fm160_net_addr_ok()`：
它见串内有 `:` 就走 **IPv6 分支**，再被**前导 v4 的 `.`** 判死 ⇒ **`has_addr` 恒 false**
⇒ `cb_ip()` 五次后报 `no address appeared after five reads of the context`。

★ **即使修好 (1) 仍会失败** —— 两个缺陷必须一起修。
★ 顺带：`dns1/dns2` 也被塞成 `"218.2.2.2,240e:5a::6666"` 这种两地址串，同法处理。
★ **`<state>,<cid>` 与 `<cid>,<state>` 的字段序仍未实测区分** —— `state==cid==1` 时两者同形。
代码注释原以为是 `raw[0]=cid, raw[1]=active`，**只因巧合一致，从未实测区分**。⇒ **故意不动**，留疑。

### 11.7 ★★★ 反直觉读数：`up: no` 不等于断网

### 11.8 ★★★ ECM 不下发 v6：两道门都关着，第一道在宿主侧

## §12 ★★★★★ v6 真收口（同日追加）：模组**不发主动 RA、但每问必答**；真根因 = `usb0` **不在任何防火墙 zone**

### 12.1 窗口为什么是 720 s
RFC 4861 `MaxRtrAdvInterval` 默认 **600 s**（`MinRtrAdvInterval` 200 s）
⇒ **720 s 才跨过一个完整周期**。§11 的 300 s、更早的 12 s 都**不构成结论**。
脚本 `181-ecm-v6-ra-long.sh`（唯一写入 `accept_ra=2`，同一运行内回滚）。

### 12.2 ★★★ 结果：三种判据要一起看
```
① accept_ra=2 在窗口内**每一个采样点**都=2（netifd 没回改）⇒ 实验有效
② 720 s 内：RA(134)=0   RS(133)=0
③ ★ 但同窗口内，模组**每 ~128 s 主动发一次 MLD query**
   （源 MAC 18:2c:7f:71:41:6f / link-local fe80::182c:7fff:fe71:416f）
```
⇒ **结论的正确措辞：不发【主动】RA，但每问必答**（phase B 真发 RS 后 `RS=4 / RA=4`，1:1）。
③ 是关键：它把「0 个 RA」限定成「没有路由器在广播」，而不是「链路死了/不支持 v6」。

### 12.3 那份 RA 的内容（phase B，实测）
`240e:478:1610:26e5::/64`（`Flags [onlink, auto]`、valid/pref infinity）、
rdnss `240e:5a::6666`+`240e:5b::6666`、router lifetime 65535s、`Flags [other stateful]`、
pref medium、MTU 1500、SLLAO `1a:2c:7f:74:44:72`（= v4 网关 ARP MAC）、**Cur Hop Limit 0**。
⇒ 前缀是 **A 标志（SLAAC）不是 M/O** ⇒ 地址由 SLAAC 就能装上。
★ `accept_ra=0→2` **不会**让内核发 RS；要发得 `disable_ipv6 1→0` 反弹。

### 12.4 ★★★ 已排除的门（都实测过，别重做）

### 15.4 ★★★★★ 真缺陷：SLAAC 客户端的 `/128` 落在 usb0

「只做 SLAAC、还没发任何流量」的客户端，其地址已经有

源码机制（odhcpd 2025.10.02，构建机 grep）：

```c
netevent NEIGH6_ADD → setup_route(addr, iface, add)
setup_route(): if (iface->learn_routes) netlink_setup_route(addr,128,iface->ifindex,NULL,1024,add)
config.c:275  iface->learn_routes = 1;                     ← 默认开
config.c:1466 iface->learn_routes = blobmsg_get_bool(c);   ← uci ndproxy_routing
```

三点：① 路由装在**邻居条目所在接口**上（条目在 usb0 ⇒ 装到 usb0）；
② usb0 上会有条目，因为**我们不做 NAT**（转发的包带客户端源地址）+ relay 把 **DAD 请求**
echo 到所有其他 relay 接口（`handle_solicit` 里的 `(ns_is_dad || !c->external)` 那一支，含 external）；
③ `ping6()` 用的是 **metric 128 且加完立刻删**，不是残留的来源 —— 实测残留**全是 1024**。
致命点：`/128` 长于 `/64`，**最长前缀优先于 metric** ⇒ 压过插件的 `metric 100`，
包被送去模组、模组邻居又指回我们 = 环形丢包；且客户端走了路由还留着。

修：`ndproxy_routing='0'` 落在 **wan 侧**段 + `wan_route_cleanup()` 清已在内核的残留 +
纳入 `odhcpd_configured()` 幂等比较（否则升级设备「已配置」而漏掉）。

## 16. 「v6 extend prefix」= RFC 7278：和我们做的是同一半，但没有另一半（22:12–23:00）

**起因**：`github.com/momokind/luci-app-hypermodem`（公开，3 commit，停更 2024-01-05）
在 `root/etc/init.d/hypermodem` 里设 `uci set network.<if>.extendprefix='1'`。问能不能解决 §40/§41 的问题。

### 16.1 它是什么

**不是把 /64 变长**，而是把「只能当 WAN 地址用的那个 /64」**提升成委派前缀**再交给 `ip6assign` 分配。
RFC 7278 的标题就是这个：*Extending an IPv6 /64 Prefix from a 3GPP Mobile Interface to a LAN Link*。

```
/lib/netifd/proto/dhcpv6.sh:17    proto_config_add_string 'extendprefix:bool'
/lib/netifd/proto/dhcpv6.sh:123   [ "$extendprefix" = "1" ] && proto_export "EXTENDPREFIX=1"
/lib/netifd/dhcpv6.script:91-93   # RFC 7278
                                  if [ "$mask" -eq 64 -a -z "$PREFIXES" -a -n "$EXTENDPREFIX" ]
                                          proto_add_ipv6_prefix "$addr/$mask,…"
```

**不是 hypermodem 的发明**：`uqmi.sh:448`（`# RFC 7278: Extend an IPv6 /64 Prefix to LAN`）、
`3g.sh:107`（`set EXTENDPREFIX=1`）—— 官方对模组就是这么干的。

### 16.2 单变量对照（256/257/258，三次复现）

```
关:  /64 dev usb0 proto static metric 256  +  /64 dev br-lan metric 100（插件）
开:  /64 dev br-lan proto static metric 1024   ← usb0 那条【消失】
     + br-lan 新增 240e:…:2000::1/64；ecm6.ipv6-prefix 出现且 assigned 给 lan
```

**★ 它把这个 /64 的『家』整个从移动接口搬到 LAN** —— 那条 `metric 256` 不再存在，
插件那条 `metric 100` 打的是一场本不该打的仗。

### 16.3 端到端判决（259，真客户端）

撤掉客户端的 `/128` + 撤掉插件那条 metric 100，只留 netifd 的 /64：
`ping6 240e:…::391` → **64 bytes, time=0.466 ms 通** ⇒ 路由层面它可独立承载 LAN。

### 16.4 ★ 它做不到的那一半（真正的难点）

usb0 邻居表里赫然有 `240e:…::391 lladdr 72:8e:08:b6:a4:a1 router` ——
**模组把 LAN 客户端当成自己链路上的邻居**。这是 3GPP 侧语义，与 netifd 无关。⇒
**odhcpd ndp relay 仍必需；wan 侧 `ndproxy_routing='0'` 仍必需**（否则 §41 的 /128 重演并压过 /64）。

### 16.5 两条 netifd 源码要点

- `interface-ip.c:1167` assignment_length 合法域 **48..64**；`lan` 的 `ip6assign 60` 面对 /64 池
  **不报错**，直接把整个 /64 给 LAN（mask 64）。⇒ 想要独立子网必须有**真 PD**。
- `interface-ip.c:756-773`：off-link 地址会加一条 `unreachable <pfx> metric INT32_MAX` 的
  null-route，注释原话 *"add null-route to avoid routing loops"* —— **netifd 早知道这个场景会成环**。

### 16.6 回滚残留 + 结论

关掉开关后 netifd **不撤**它装的地址（残留 `240e:…:2000::1/64 deprecated dynamic`），路由会撤。
⇒ **对现状无净收益**：现状已工作且不依赖 netifd 内部行为。**建议保留现状**，
把 `extendprefix` 记成「同一件事更规范的官方实现」，将来重构插件（想省 state 机）时可考虑。

### 16.7 ★ 本段探针缺陷

**`ip -6 route show` 打印主机路由时不含 `/128` 后缀** ⇒ `grep '/128'` 漏掉全部主机路由（假阴性）。
258 因此误报 `client: none`，实际有两个活跃客户端。
**判据用 `ip -6 route get <addr>`；要分族就 `grep -F "$PFX" | grep -F '/64'`。**

## 19. 首次真机发短信：模组在"命令层"拒绝 MO 短信（2026-09-21 晚）

目标：把 `fm160d` 的发送路径（M3，9/19 提交 `d10a134`，当时**无卡**，只验了无卡降级）在真机上跑通，
发往 `+86 <手机号-A>`。

### 19.1 现场

```
设备 iStoreOS 24.10.8 r29755, rockchip/armv8, kernel 6.6.144
模组 Fibocom FM160-CN, rev 89614.1000.00.04.01.02, 2cb7:0105, GTUSBMODE 33 (ECM)
AT 口 /dev/ttyUSB2 —— 唯一持有者是 ubus-at-daemon(PID 5971, fd 9)；fm160d 是它的 ubus 客户端
                            （走 sendat 的 at_cmd / raw_at_content 两个字段）
SIM  ICCID <ICCID> / IMSI <IMSI> ⇒ 中国电信；CPIN READY
注册 CEREG 0,1(CEREG/C5REG/CGATT 全 1)；COPS 0,0,"????",11 ⇒ act=11 = NR connected to 5GCN (SA)
CSCA "+8613344181200",145；CSQ 99,99（无信号读数，属正常）；CGDCONT cid2 = "ims"（未激活）
```

### 19.2 ★★★★★ 发送前先彩排：`AT+CMGW` 走同一条两阶段

发送路径此前**从未在真机跑过**。两阶段传输（提示符 `>` → 原始载荷 → Ctrl-Z）是最大未知，
而它若在阶段 2 断掉，模组会一直等消息数据，**下一条 AT 命令会被当成消息正文** ⇒ 串口卡死。

所以先做彩排：`AT+CMGW`（写入模组存储，不发网）走**完全相同**的两阶段，模组同样解析 PDU。

```
阶段 1  AT+CMGW=62                        → 26 ms 收到 ">"          ✓
阶段 2  126-hex PDU + 1A                  → 23 ms "+CMGW: 1" + OK   ✓  ← 模组完整解析了我们的 PDU
清理    AT+CMGD=1                         → ME 回到 0/127           ✓
```
⇒ 传输与编码都已被独立证明。附带确认了一件容易搞混的事：`sms.last_pdu` 里存的是
**双倍 hex**（126 字符 PDU → 252 + "1A" = 254），所以 `pdu_chars` 的期望值是 **254**，不是 126。

### 19.3 ★★★★★ 真发失败，且失败在"命令层"

`ubus call fm160 sms_send` → `{"status":"error","response":"\r\n\r\nERROR\r\n"}`，
`sent_fail++`、`done_segments=0`、`mr=-1`。

**我们这侧的三个自证都吻合**：`command=AT+CMGS=62`、`pdu_chars=254`、`segments=1`
（与独立参考实现 `sms_pdu_ref.py` 的预测逐项一致）⇒ **编码器无罪**。

然后按层剥离：

| 实验 | 结果 | 排除了什么 |
|---|---|---|
| 同长度 `AT+CMGW=62` | `+CMGW: 1` OK | 长度语义、PDU 语法 |
| 文本模式 `AT+CMGS="+86…"` | **裸 ERROR, 87 ms** | **我们的 PDU**（模组自己建 PDU 也失败） |
| `AT+CMSS=<idx>`（从存储发） | **裸 ERROR** | CMGS 事务本身 |
| `AT+CMEE=2` 后重试 | 仍是裸 `ERROR` | 「错误码被压制」 |
| `AT+CGSMS=0/1/2/3` | 四种全失败（85–87 ms） | MO 短信承载选择 |
| `AT+CSMS=1` | 同样失败 | 短信服务语法版本 |
| `AT+CGACT=1,2`（拉 IMS 承载） | **模组回 ERROR**，不让激活 | IMS 承载缺失 |
| `AT+CLCK="FD",2` | `+CLCK: 0` ⇒ FDN 未启用 | 固定拨号限制 |
| `AT+CFUN?` `AT+CPIN?` `AT+CPMS=?` | `1,0` / `READY` / `("ME","SM")` | 功能受限、卡异常、存储不支持 |

**关键判据（三层，互为对照）**：
1. **手册写明 CMGS 失败应回 `+CMS ERROR: <err>`**（§7.1.16），而实测是**裸 `ERROR`** ⇒ 拒绝发生在
   短信业务层**之下**，是命令层拒绝。
2. **时长恒定 85–87 ms** ⇒ 本地拒绝，不是网络往返（网络往返是秒级）。
3. **同一串字节 `CMGW` 收下、`CMGS` 拒绝** ⇒ 分歧只在"要不要交给网络"这一步。

⇒ **结论：`fm160d` 的发送路径代码正确；拒绝来自模组/SIM/网络侧，AT 层无开关可解。**
最可能是该卡（电信 5G SA 数据卡）的订购关系不含 MO 短信，或该卡在 SA 下没有可用的短信承载。
**下一步只能靠外部验证**（把卡插手机试发 / 问运营商），或模组整机复位（见 19.5，未执行）。

### 19.4 ★★★ 我自己踩的两个坑（都写进了脚本注释）

1. **无条件"drain"把串口搞脏**：探针 262 在阶段 1 已给出提示符的情况下，仍先发了一个孤立 Ctrl-Z
