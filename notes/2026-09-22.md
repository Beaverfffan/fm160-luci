## 2. ★★★★★ 制式是决定变量：同一条命令，两种完全不同的行为

本次最重要的发现。同日、同字节、同承载（CGSMS=2），**只因制式不同**：

| 探针 | 制式 | 承载 | `AT+CMGS` 结果 | 含义 |
|---|---|---|---|---|
| 273 | **NR SA** (act=11) | CGSMS=2 | `ERROR` **88 ms** | 本地秒拒 |
| 278 | **NR SA** (act=11) | CGSMS=2 | `ERROR` **90 ms** | 复现一致 |
| 272 #4 | LTE (act=7) | CGSMS=1 (CS) | `ERROR` **94 ms** | 无 CS 域，合理 |
| 272 #2/#3 | LTE (act=7) | CGSMS=2 | 客户端 30 s 截断 | 观察窗口不够（见 §3） |
| **276** | **LTE** (act=7) | CGSMS=2 | `ERROR` **40010 ms** | **T1_RP 超时** |

**40010 ms = 40 秒 = 3GPP TS 24.011 的 T1_RP 默认值。**

⇒ 语义完全不同：

- **NR SA**：模组在**命令层本地秒拒**（~90 ms，无网络往返）。与昨天在 NR SA 下的全部读数一致。
- **LTE**：模组**接受并真的把 CP-DATA 提交下去**，然后等 RP 应答，**满 40 秒没有应答**才放弃。

这**订正了昨天的结论**：昨天写的「拒绝在模组命令层」只在 NR SA 成立。正确的表述是
**制式决定行为**。

## 3. ★★★ 排除「40010 是我们自己的超时」（三个可能的伪造源都查了）

1. `at-daemon/src/const.h:11` `#define DEFAULT_TIMEOUT 5 // seconds` ⇒ 超时单位是**秒**；
   `main.c:179` 直接把 blob 里的值取出来用，**不做 clamp**；`at_handler.c:210`
   `abs_timeout.tv_sec += timeout` ⇒ 我们传的是 280 秒 ⇒ at-daemon 没掐断。
2. **`ubus call` 客户端自己有 ~30 秒上限** —— 275 的运行日志 `start 09:37:09 / end 09:37:39`
   只有 30 秒，不是请求的 240 秒。`ubus -t <seconds>` 可以抬掉这个上限。
   ⇒ **昨天所有「沉默」判读的观察窗口其实都只有 30 秒**，而 T1_RP 单次就要 40 秒。
3. 手册 GT 族 27 条命令里**没有一条与短信有关**（`AT+GTACT/GTAUTOCONNECT/GTRAT/…`），
   即这种 40 秒等待不是某个可配的厂商定时器。

⇒ **40010 ms 只能来自模组自己。**

### 13.2 ★★★★★ 模组复位后，插件的短信布防是**陈旧的**（真缺口）

复位把模组的 NV 打回默认：

```
AT+CNMI?  →  0,0,0,0,0     ← 新消息通报被关掉（复位前插件设的是 2,1,0,0,0）
AT+CPMS?  →  "SM",0,40     ← 存储回到 SIM（复位前插件设的是 ME）
```

而插件这边：

```
probe_cb()         只重置 port / port_found / at_state，**没有清 g_state.sms.setup_done**（sched.c:439-452）
sms_setup_kick()   见 setup_done 为真直接 return（sms.c:828）
sms_sync()         见 setup_done 为真就跳过重新布防，只做 AT+CMGL=4（sms.c:907）
```

⇒ 状态机停在"布防好了"的假象里（`setup_done=true, storage=ME, age_ms=219634`），
**实际模组已经停止通报新短信**。后果：MT 短信会静默躺进模组存储，插件永远看不见。

日志实证：复位后插件**确实**重新识别了模组（`reading module identity` → `identity: … imei=<IMEI> mode=33`），
**但没有**任何 `sms storage set to ME` / `sms ready` 跟进。

**建议修法**（未实施，等用户裁定）：`fm160_cmd_ident_start()`（cmds.c:770）里清 SMS setup 状态
（`setup_done=false`、`st.mem[0]='\0'`、`cmgf_known=false`、`setup_tries=0`），并 kick 一次 sync。
identity 重读正是"面对的是一个新模组"的判定点，语义天然吻合。

本次为了能收到用户的 MT 测试，已**手工补回**：`CMGF=0`、`CPMS="ME","ME","ME"`（→0,127）、`CNMI=2,1,0,0,0`。

### 14.2 ★★★★★ 两条纠正（都有本机实测/厂商手册支撑）
1. **这个固件没有任何 IMS 状态命令。** 实测全部 ERROR：
   `AT+CLAC`→裸 OK（不提供命令表）；`+CIREG? +CIREP? +CIMS? +GTIMS? +GTIMSSTATE?
   +GTVD? +GTIMSEN? +GTUICCIMS? +CPAS?` 全 ERROR。
   厂商 130 条命令手册（`_ref/fm160/docs/at/`）里**唯一** IMS token 是 `+CAVIMS`。
   ⇒ 那份流程的"第 2 步"**在 FM160-CN 上不可执行**；`+CIREGU`/`+VOICE REG` 不是广和通命令。
2. **`+CAVIMS` 不能当"IMS 已注册"用。** 手册：set 是"informs the **MT**"，
   read 返回"status **stored in the MT**" ⇒ 是存量标志，非实时注册。

## 17. ★★★★ 插件层接力（2026-09-22 晚，Kimi 接力 DeepSeek 工作区）

**背景**：FOTA 升级到 `89614.1000.00.04.01.23` 后 AT 层短信双向已通（§15 根因订正确认），
但**插件（fm160d）层的 SMS 全链路从未被真机验收过**——DeepSeek 时代只验到 AT 层。
本节把插件接收链路三个真 bug 全部抓住并修复，收发双向端到端验收通过。

### 17.1 修复一：模组重识别后 SMS 布防不重跑（既有缺口，§15 末尾已立案）

- 根因：`fm160_cmd_ident_start()` 重置端口/AT 状态机，但不清 `sms.setup_done`；
  模组复位（CNMI→`0,0,0,0,0`）后状态机永久停在"已布防" ⇒ 再也收不到 `+CMTI`。
- 修法：新增 `fm160_sms_setup_reset()`（sms.c:806，置 setup_done/running/cmgf/step/tries），
  在 `ident_start`（cmds.c:774）里 `fm160_ident_reset()` 之后调用。
  调用点只有两处（sched.c 端口重现 / ubus 手动刷新），两处都正确。
- **真机验证**：装机后 `AT+CFUN=1,1` 软复位 ⇒ 模块 CNMI 回到 `0,0,0,0,0`
  ⇒ daemon 自动重跑 setup 链（CMGF=0 → CPMS → CNMI=`2,1,0,0,0`），零人工干预。✓

### 17.2 ★★★ 修复二：`+CMTI` 索引解析遇逗号变 0（历史 bug，接收路径从未工作过）

- 现场：`new message announced: +CMTI: "ME",1` 后 `reading message 0 from ME failed (AT+CMGR=0 ERROR)`。
- 根因：`sms.c` URC 解析 `index = atoi(e + 1)`，而 `e` 指向**闭引号**，`e+1` 是 `",1"`，
  `atoi` 遇逗号即停返回 **0** ⇒ 永远读索引 0，真短信留在存储里。
  **这意味着插件短信接收从来就没通过 daemon 成功过**（旧固件时代也没人验到这一层）。
- 修法：`atoi(e + 1 + strspn(e + 1, " ,\t"))`。
- 教训：**引号闭合约定的偏移最容易忘**——凡是"指针停在分隔符上再 atoi"的写法都要审查。

### 17.3 ★★★ 修复三：`strstr(resp, "+CMGR")` 命中命令回显，PDU 被吃掉

- 现场（修完 17.2 后）：`cannot decode a stored PDU at ME,2: not hexadecimal`。
- 根因：响应原文 `AT+CMGR=2\r\r\n+CMGR: 1,,33\r\n<PDU>…`，`strstr` 先命中回显里的
  `+CMGR` ⇒ 从回显行尾切出的"PDU 行"其实是 `+CMGR: 1,,33` ⇒ `parse_hex` 在 `+` 处失败。
  讽刺的是同文件**头部检查**用的是 `fm160_resp_find()`（带行首守卫，正确），
  取 PDU 位置时却退回裸 `strstr`——同一个解析器两套标准。
- 修法：`fm160_parse_cmgr` 改成与 `fm160_parse_cmgl` 相同的行首守卫循环。
- 附带：unread 在 +CMTI 通知时和 PDU 入库时**各加一次**的双计数，删通知侧那一笔。

### 18.1 MBIM 模式（GTUSBMODE 30）实测结论：拨号可用，但有 3 个非显然坑

| 项目 | 结果 | 证据 |
|---|---|---|
| 注册/Attach | ✓ | `umbim registration` home，`cereg/c5greg = 1` |
| 拨号（v4+v6 双栈） | ✓ | wwan0 = 10.17.145.227/29 + 240e:400:1610:141a:…/64 |
| 连通性 | ✓ | ping 223.5.5.5 / 240e:5a::6666 各 3/3 |
| 测速（TUNA 镜像 30MB） | ~8.5 MB/s（≈68 Mbps） | curl -r 0-30000000 |
| SMS | ✓ | mode 30 保留 AT 口（ttyUSB0），sms_send 秒回 OK |
| GNSS | 未深验 | AT 口在，原理可用（天线问题与拨号模式无关） |
| LAN IPv6 前缀 | ✗ 缺代理 | /64 被 netifd 装到 br-lan，但 wwan0 无 proxy neigh、odhcpd 无 wwan 段，LAN 客户端 v6 出向不通 |

**坑 1（固件行为）**：Fibocom 固件的 MBIM connect **拒绝显式 APN**——`connect ctnet` 立即
`activationstate 0003 deactivated`；`connect ''`（设备默认 APN）→ `0001 activated, ipv4v6`。
而 netifd 自带 `/lib/netifd/proto/mbim.sh` 硬性要求非空 APN（`[ -n "$apn" ] || NO_APN`）。
⇒ 必须 patch 系统脚本两处：① 放行空 APN；② connect 调用在空 APN 时只传 `"$req_pdptype"`。
**系统文件，固件升级即丢**——这是开源工具链的第一个缺口。

**坑 2（umbim 语义）**：umbim 的 `-t <tid>` 同时意味 **跳过 MBIM OPEN 握手**（cli.c:
`case 't': no_open = 1`）。stock mbim.sh 的流程依赖首条 `umbim -n caps`（无 -t）建会话、后续
全用 -t、teardown 时 CLOSE。手动调试若首条就带 `-t`，模组回 FUNCTION_ERROR（not opened），
表现为"MBIM 通道假死"——本次误判为固件卡死，白走了 CFUN 重启/驱动重绑一整圈。
⇒ 手动 umbim 必须先发一条无 -t 命令建会话；`-n` 只控制"结束时是否 CLOSE"。

**坑 3（补丁工程）**：`mv file.new file` 丢失目标执行位（644），netifd 起 proto 脚本直接
exec 失败 → 秒级 setup/down 空转循环且**无任何脚本输出**（连 NO_DEVICE 都没有），极具迷惑性。
⇒ 补丁脚本收尾必须 `chmod 755`。

### 18.2 与 ECM 的实质差异（初步）

- ECM：模组内置协议栈 + RA，前缀天然含 LAN 委托语义；fm160-prefix 全套围绕 usb0 建立。
- MBIM：主机协议栈；v6 地址/前缀来自 `umbim config`（静态装进 wwan0），netifd 把同一 /64
  也装进 br-lan，但**没有任何组件在 wwan0 上答 LAN 客户端的 NS**（无 proxy neigh）。
  要补齐需 odhcpd ndp=hybrid 或把 fm160-prefix 的代理逻辑移植到 wwan0 —— 待 QMI 后统一收尾。

- V1.0.5 驱动 `/sys/class/net/wwan0/qmap_mode` 是 **r--r--r--**（文档 V1.0.3 里可写），只能模块参数设：rmmod + `insmod qmi_wwan_f.ko qmap_mode=2` 成功出 wwan0.1/wwan0.2。

2. QMAP 单流问题需广和通支持介入（驱动 V1.0.5 QMAP DL 路径单流状态机），报障时可附本节证据表。
3. 若必须 QMAP 且要多流并行才能跑满，注意 wwan0.1 子设备统计计数有 bug（TX 字节数异常巨大）。

## 22. ★★★★★ QMAP 彩票根因定位：排除注册/信号/TCP，锁定模组 QMAP DL 调度（2026-09-22 23:16–23:50，用户指令「单纯检查qmi，看看是否是否和nr注册有关」）

### 排查链（每条都有对照实验）
1. **NR 注册？** 排除。10 轮采样 DataCap 恒为 NR5G、C5GREG 恒 1，速度 2.7–13 MB/s 乱跳。
2. **服务小区质量？** 排除。fm160d 状态（earfcn 627264 / pci 354 / rsrp -106 / rsrq -14.5）10 轮完全相同（注意：该状态缓存 ~17s，不作为实时证据）；改用 AT+CESQ 实时值做 12 轮采样，信号原始值几乎不动，速度 2.0 ↔ 16.6 交替。
3. **镜像源/服务器？** 排除。USTC 三连 2.8 曾像"固定慢"，但下一轮 USTC 又跑到 7.9；TUNA 依旧 2.2–15.7 乱跳。多源同模式。
4. **MBIM 对照软化**：ABAB 交替测中 MBIM 也出现 12.5/13.1（此前恒 19+），说明**时段因素存在但不主导**；QMAP 的离散度仍显著大于 MBIM。
5. **TCP 层机制（决定性）**：对比慢/快运行的 /proc/net/netstat TcpExt 增量——
   - 快（10MB/s）：TCPOFOQueue +8768、TCPRcvCollapsed +8123、TCPAckCompressed +4436（burst 交付 + 乱序特征明显）
   - 慢（0.8/1.7MB/s）：**几乎没有任何到达计数器**（OFOQueue +2、RcvCoalesce +200~400）
   - 即：慢的时候**数据根本没到主机**——不是丢包（无 Retrans）、不是拥塞（无 RTO）、不是窗口。模组的 DL QMAP 聚合对该流只吐出涓涓细流。

### 结论
- 与 NR 注册、信号质量、服务器、主机 TCP 栈全部无关。
- 机制在**模组固件的 QMAP DL 聚合/调度内部**（按流状态机），host 侧无法观测更细。属固件缺陷，建议报广和通（证据：本节 + §21 全部对照表）。
- 主机侧规避：多流并行（已验证 19–22MB/s）或直接用 MBIM。
